How a page runs a program#

A page loads blimp.js (the interpreter, as WebAssembly) and blimp-view.js (the host), fetches a .blimp file and mounts it:

var view = new BlimpView(blimp, containerEl, { send: true })
view.mount(source, 'game')   // the source ends with: game <- :view

The program's last expression must be a view: that is the first render. From then on every event is a message to that one actor, followed by :view, and the page is patched to the new view. In { send: true } mode both go through blimp.send rather than evaluating source text, so a page that runs for an hour does not keep an hour of evaluations.

The actor is the page's one top-level variable. A message from the page is game <- :msg or game <- :msg(args), and its arguments are Blimp values written out as source: a string arrives as a String, a form as a Map, with: 3 as an Int.

Messages from outside a render (a socket frame, a stored value, a fetch's answer) are held until the current render has finished, so none lands in the middle of one. A socket's messages go through one queue and reach the program in the order they came.

el#

el(tag, attrs, children...) is a real element with the page's own classes and attributes. to_html prints what the page gets:

puts(to_html(el("p", %{class: "note"}, "hello")))
<p class="note">hello</p>

to_html works on the command line and in the browser alike, so a test that checks a view's markup passes in both. Instructions and effect nodes never appear in it: it is the page without its program.

Tags. The common HTML elements, SVG (svg, g, path, circle, rect, line, polyline, polygon, text, tspan, defs, gradients, ellipse, title) and dialog. Nothing that loads or runs a document of its own: no script, iframe, object, embed, style, link, meta or base. An unknown tag is a TypeError.

Attribute values are strings, numbers, atoms, booleans or nil. true writes the bare attribute (disabled), and false or nil leaves it out. A key starting with on is refused, and so is a javascript: URL, however it is spelled, in href, src, action, formaction, xlink:href or poster.

class: and style: take data. A class can be a list of names (with nil, false and "" left out) or a map of names to booleans. A style can be a map, where a nil or false value leaves the property out. They are turned into text inside el(), so the page sees exactly what a string would have given.

puts(to_html(el("li", %{class: %{note: true, fresh: true}}, "hi")))
puts(to_html(el("li", %{class: ["note", nil, "fresh"]}, "hi")))
puts(to_html(el("div", %{style: %{translate: "12px 4px", "z-index": 4, color: nil}}, "x")))
<li class="note fresh">hi</li>
<li class="note fresh">hi</li>
<div style="translate: 12px 4px; z-index: 4;">x</div>

Numbers are written as they are: "z-index": 4 is right, and a width wants "12px". A class or style map whose key is a Blimp keyword (on, do, end, when) has to quote it: %{"on": true}.

Children, and show#

Children are strings, nodes, or lists of either; a list is spliced in, one level deep. A child that is nil or false is nothing, so a helper can return nil for "nothing here".

show(cond, node) is node when cond is true and nothing when it is false. It is lazy: node is only built when cond is true, so it may read what cond guards. cond must be a Bool.

q = nil
puts(to_html(el("div", %{}, show(q != nil, el("p", %{}, q.text)), "after")))
<div>after</div>

(The first show, #89, built node first. Its first real use was the line above, and q.text failed before show saw the condition. #93 made it lazy.)

Instructions on el#

These keys in the attribute map are instructions to the page, not HTML. They never reach the markup:

puts(to_html(el("form", %{submit: :post, reset_on_submit: true},
  el("textarea", %{name: "text", submit_on_enter: true, focus: true}))))
<form><textarea name="text"></textarea></form>

Forms#

submit: sends the form's fields as a map with quoted keys, so f.name, lookup(f, :name) and lookup(f, "size-pick") all read it:

on :post(f: Map) do
  text = f.text
  ...
  • A text field, textarea or select is its value, as a String.
  • A checkbox is true or false.
  • A group of radio buttons is the value of the checked one, and absent if none is checked.
  • Disabled fields, fields without a name, and buttons are left out.

Until #90 it was one JSON string, every handler started by decoding it, and every radio wrote its value whether checked or not.

To empty the form after sending, use reset_on_submit: true on the form. The trick of changing the field's id so that a new element replaces it also loses the focus.

Dialogs#

show(confirming, el("dialog", %{modal: true, dismiss: :cancel},
  el("p", %{}, "Take this note down?"),
  el("button", %{click: :delete}, "Take it down")))

A dialog is open while it is in the view and closed when it is not. modal: true opens it with showModal(), which gives a ::backdrop, keeps the focus inside, and makes the page behind it inert; without it, show(). dismiss: :msg is sent on Escape (the browser is told not to close it, so the program decides) and on a click on the backdrop, which is a click on the dialog element outside its box. A click inside the box, even on its padding, is not a dismissal.

An overlay div with click: :close is the wrong shape, because only the innermost click: runs: a click on the dialog's text has nothing closer to land on than the overlay, and closes it.

The browser's dialog comes with its own border, padding and position. Style dialog and dialog::backdrop in the page's CSS.

Effect nodes#

These go anywhere in the view and draw nothing. After each render the page makes its timers, listeners, requests and storage match them.

puts(to_html(el("div", %{}, stored("k", :got), store("k", "v"), timer(1000, :tick), "only this")))
<div>only this</div>
NodeWhat it does
timer(ms, :msg):msg every ms milliseconds while it is in the view.
key("ArrowLeft", :msg)That key sends :msg, anywhere on the page except in a field, and not with Ctrl, Cmd, Alt or Shift held.
key("*", :msg)Every key: :msg("a"), :msg("Enter"), not prevented.
key("ArrowUp", :down, :up)A held key: :down once when it goes down and :up when it comes up; auto-repeat is not sent.
fetch("/path", :msg)One GET to the page's own server while it is in the view: :msg(status, body), status 0 if it failed. Asked for again after it leaves the view and comes back.
location_query("a=1")The page's URL carries this query string (replaced, not pushed: no history entry per click).
stored("key", :msg)Reads key from localStorage once, and sends :msg(value), "" if nothing is there.
store("key", "value")localStorage holds value under key; "" removes it. Written only when it differs. A key is not written while a stored() read of it is on its way, so a page's first render cannot overwrite what it is about to read. Storage that refuses (a private window) reads "" and drops writes.
socket(...)A WebSocket. See below.

socket#

socket("/live/aim", %{frame: :frame, open: :connected, closed: :offline, sent: :sent},
       out_first, outbox)

While the node is in the view, the page holds a WebSocket to that path on its own server (ws:// or wss://, as the page is); a path to another host, //host, is refused. A drop is redialled after 0.5s, doubling to 10s, until the view lets it go.

  • frame: (required): each text frame that arrives is :frame(text), in the order it came.
  • open: and closed: (optional): each connection and each drop.
  • sent: (required), out_first and outbox: the program's queue of frames to send, the first numbered out_first. The page sends each number once, in order, while connected, and answers :sent(n), the last number it has sent, so the program can drop them.
on :sent(n: Int) do
  become outbox: drop(outbox, n - out_first + 1), out_first: n + 1
  reply :ok
end

(Blimp has no drop builtin. Write one, as bobbby.online's aimp_drop.) Frames still waiting when the socket drops go up when it is back, unless the program drops them in its closed: or open: handler, which is the program's call. /aim signs on again instead.

How a render patches the page#

A render patches the page it drew last, rather than drawing a new one. An element whose node did not change is the same element afterwards, with its focus, selection, scroll position and playing media. The rules for when an element is kept:

  • A different tag is a new element.
  • A different id is a new element. This is how a CSS animation restarts, or a sound plays again: el("audio", %{id: concat("s", to_string(n)), src: ..., autoplay: true}).
  • A changed attribute is set on the same element. An instruction that needs a listener the element does not have makes a new element.
  • Children are matched by key: when every child has one. A kept key keeps its element, patched; a new key is a new element; a key that went is removed. A kept element is moved only if the order of the kept ones changed, because a moved <iframe> reloads. Two children with one key is an error: el: two children have key: 5.
  • Otherwise children are matched by position: the children both views have are patched, and the rest are added or removed. That is right for a list that grows at the end, like a chat log, and wrong for one that grows at the top, which wants key:.

Before #85, an element whose number of children changed was rebuilt. A chat log lost its scroll position with every line, and an <audio autoplay> in a parent that gained a child played again.

The clock in the browser#

WebAssembly has no clock, so blimp.js hands the page's in before every evaluation and message (blimp_set_clock):

  • now() is seconds since 1970.
  • now_ms() is a monotonic clock in milliseconds (performance.now()), for measuring, not for dates.
  • utc_offset() is seconds the reader's zone is ahead of UTC: -14400 in New York in summer.
format_time(now() + utc_offset(), "%I:%M %p")   # "03:42 PM": %I pads the hour

On a server utc_offset() is the process's zone (TZ), which in a container is usually UTC: 0. A host that never calls blimp_set_clock reads zeros, as every browser did before #84. seed(n) seeds random; a page should call it once, with the time, or every visitor gets the same numbers.

The older builtins#

Before el there were builtins for common shapes, and the host still draws them, each with a blimp- class to style: stack, row, grid, text, heading(text, level), bold, italic, code, code_block, blockquote, divider, list, link(label, url), image(src, alt), video, canvas, button(label, :msg), and draw(w, h, ops), a canvas painted from a display list. Tutorial chapter 8 uses them.

form, input, textarea, select, option and mount_root are builtins too, but blimp-view.js has no case for them: in a browser page they render as a plain <div>, and a form made with form() sends nothing. Use el("form", ...).

What it does not do#

  • No <script>, <iframe> or <style>. A YouTube embed on bobbby.online is inner_html, built and checked by the program.
  • No scrolling to a place other than scroll: :end, and no reading the window's size: a program cannot tell a phone from a laptop except by CSS.
  • No binary frames on a socket, only text. A frame is the program's to decode, usually with json_decode, which turns atoms into strings and tuples into lists.
  • No trim, starts_with, ends_with, drop or take in Blimp itself. bobbby.online gets them from its Temper library or writes them per program.
  • One actor per page talks to the host. It may spawn others and send them anything, but every event goes to the one named at mount.
