Blimp runs bobbby.online.

Blimp is an actor language with a tree-walking interpreter written in Zig. One blimp --serve process answers most of bobbby.online: the homepage, the blog, about forty other pages, their WebSocket rooms, a Postgres client, outbound HTTPS and a Bluesky firehose. The same interpreter, compiled to WebAssembly, runs the games and tools on those pages in your browser.

Much of the site's pure logic is written in Temper and compiled to Blimp. A web framework is being written in Blimp so the last Phoenix pages can move over. This page is the state of all that on 30 September 2026, with what does not work yet listed by name.

0Start here: build Tetris

The way to learn Blimp is the tutorial, which builds the Tetris that runs on bobbby.online/tetris (the same program), one actor a chapter. Each chapter has an exercise in the page: an editor holding the chapter's file with the handlers left for you, the tests that say when you are done, and the answer behind a tab. Nothing to install: the interpreter runs in the page as WebAssembly. In chapter 8 the game you wrote plays there too.

actor Tetris.Piece do
  state kind: Int :: 1
  state rot: Int :: 0
  state x: Int :: 3
  state y: Int :: 0

  on :rotate(dir: Int) do
    become rot: rem(rot + dir + 4, 4)
    reply :ok
  end
end

Chapter 1's piece. It does not know its shape yet; chapter 2 gives it a Tetris.Shapes to ask.

Tetris.Bag: seven pieces shuffled, and how to test something random.
6. The game takes input
Tetris.Game coordinates the rest: moves, rotation, wall kicks, pause.

A tick is one row. Landing, locking, clearing, game over.

Tetris.Screen: views are values. Then play what you built.

The finished program is examples/tetris.blimp, 801 lines with 34 tests. Chapters 3 to 8 are cut from it by exercises/build_tetris.py, so a change to the game reaches the exercises by running one script.

1One process answers the site

The production container runs a single command. There is no framework under it, no Elixir and no Node: --serve loads one Blimp file, then evaluates the tick expression forever and compacts the heap between ticks.

# blimp_site/Dockerfile
CMD ["blimp", "--serve", "_build/site.blimp", "--tick", "site <- :tick", "--control", "site.sock"]

Blimp has no imports, so build.sh concatenates the used part of the Temper output, every src/*.blimp and main.blimp into one 540 KB file. Booting it locally:

blimp blog: 16 posts rendered in 645ms, museum from data/*.tsv, listening on :4191
[serve] booted _build/site-4191.blimp; live heap 33552352 bytes; control socket .../site.sock
GET / 200 0ms

In production every response it sends carries its name:

$ curl -sI https://bobbby.online/ | grep served
x-served-by: blimp

What is in that process

  • Pages rendered at boot. The desktop homepage, /blog and every /post/*, through a Markdown renderer and syntax highlighter written in Blimp and Temper. Each post page ships the same renderer to your browser, which renders the post a second time.
  • WebSocket rooms on /live/*, each an actor stepped from the tick: Pong, Wordle, Blackjack (the tables live on the server), shared cursors, a map of pins, MTA buses (one poller for every visitor), the Bluesky firehose.
  • A Postgres client written in Blimp (src/80_postgres.blimp, 424 lines, SCRAM-SHA-256 login) over the runtime's TCP builtins. The homepage museum, /map's pins, /phish and /role-call read it.
  • Outbound HTTPS with http_start / http_result (#60). The request runs on a worker thread and the program polls for it, so a slow remote does not stop the site. Hacker News, MTA Bus Time, iCloud and the OpenAI calls behind /ziggy all use it.
  • A TLS WebSocket client, ws_open / ws_recv (#67). It holds Bluesky's Jetstream at about 38 frames a second; under --serve, five minutes of it stayed between 14.5 and 29 MB.
  • A control socket. blimp --attach site.sock is a prompt on the running program:

An actor that talks to the outside world never waits for it. This is the Hacker News poller, a state machine the site's tick steps once per tick (from src/99_hacker_news.blimp, shortened):

on :step do
  t = now()
  case phase do
    :idle ->
      case t >= next_at do
        false -> reply :idle
        true ->
          h = http_start("GET", concat(HN_API, "/topstories.json"), %{}, "")
          become phase: :ids, ids_handle: h, started: t
          reply :started
      end
    :ids ->
      r = http_result(ids_handle)
      case r do
        nil -> reply (self <- :give_up_if_late(t))
        {:ok, 200, body} ->
          ids = hn_take(elem(json_decode(body), 1), 50, [])
          ranked = zip(ids, range(1, length(ids)))
          become phase: :items, queue: ranked, flying: [], got: []
          reply :items
        _ ->
          become phase: :idle, next_at: t + 60, last_error: concat("topstories: ", to_string(r))
          reply :failed
      end
    # :items keeps up to HN_IN_FLIGHT story requests going the same way

The whole site as a graph, from Temper source through every build step, file, process and service to the page on your screen, is at bobbby.online/stack. It is itself a Blimp program drawn over a layout computed in Temper. Start there for the map of the system.

2The same interpreter runs in your browser

The Zig interpreter also compiles to WebAssembly. A page loads blimp.wasm, fetches a .blimp file from the server and runs it. The program's last expression is a view: el(tag, attrs, children...) builds real DOM elements with the page's own CSS classes, including SVG and <dialog>, and events come back to an actor as messages (click:, input:, submit: with the form as a map, swipe:, drag:, keys, timer(ms, :msg), fetch(url, :msg)). The view also holds a WebSocket (socket()), remembers between visits (stored() and store()), and keeps a list's rows by key:. draw() paints a canvas for pages with thousands of points. The view reference has every piece, and tutorial chapter 10 builds a page with most of them.

Since 1 October 2026 bobbby.online/aim has no script of its own: its chat socket, its stored screen name, its draggable windows, its sounds and its clock are all the Blimp program.

Every such page has a small window that draws that program's own actors and the messages between them, live, from the interpreter's state while you play.

# static/twenty48/twenty48.blimp: the rules are Temper (below), the actor and view are Blimp
def t48_add_tile(board: List) -> Tuple do
  empty = t48_empties(board)
  case empty do
    [] -> {board, -1}
    _ ->
      at = elem(empty, random(0, length(empty) - 1))
      value = case random(1, 10) == 1 do
        true -> 4
        false -> 2
      end
      {t48_set(board, at, value), at}
  end
end

actor Twenty48 do
  state board: List :: []
  state size: Int :: 8
  state score: Int :: 0
  # ... eleven more fields

  on :new_game do
    one = t48_add_tile(t48_blank(size))
    two = t48_add_tile(elem(one, 0))
    become board: elem(two, 0), score: 0, over: false, won: false, fresh: elem(two, 1), # ...
    reply :ok
  end
  # ...
end

el("button", %{class: "howto-start", click: :start_game}, "START")

3Temper compiles to Blimp

temper-blimp adds a Blimp backend to the Temper compiler. temper build -b blimp turns the site's Temper library (22 modules of literate Temper under blimp_site/temper/src, about 10,000 lines with their prose) into one Blimp file, and temper/prune.pl gives each program only the definitions it calls. The server never runs Java; it gets Blimp.

The rules of 2048, Wordle, Blackjack and Chess-9, the Markdown and highlighting helpers, the moon-phase math, the /stack layout and the /sky layout are Temper now. An exported Temper function compiles to a plain def with the same name, so no Blimp caller had to change:

// blimp_site/temper/src/twenty48/twenty48.temper.md
export let t48_slide_line(values: List<Int>): List<List<Int>> {
  let z = values.filter { (v): Boolean => v != 0 };
  if (z.isEmpty) { return [values, [0], []]; }
  if (!t48_any_pair(z, 0)) { return t48_pad(z, values.length); }
  let starts = t48_range(z.length).map { (k): Boolean => t48_starts(z, k) };
  let kept = t48_range(z.length).filter { (k): Boolean => k == 0 || !starts[k - 1] };
  let out = kept.map { (k): Int => if (starts[k]) { z[k] * 2 } else { z[k] } };
  let merges = t48_range(kept.length).filter { (j): Boolean => starts[kept[j]] };
  let points = merges.reduceFrom(0) { (acc: Int, j: Int): Int => acc + out[j] };
  let n = out.length;
  let padded = t48_range(values.length).map { (j): Int => if (j < n) { out[j] } else { 0 } };
  [padded, [points], merges]
}

What stays in Blimp stays for specific reasons. A Temper class becomes a Blimp actor, and actors are never collected, so every module is written as functions. Temper has no tuples, no atoms and no case mapping on strings, so records, anything that lower-cases, and parsers that return tagged tuples stayed Blimp. Actors and views are Blimp by design.

Temper's output has many top-level names, and that exposed two costs in the interpreter: top-level lookup walked a list, and every closure copied every global. #64 put the globals behind a hash table:

boot (data/*.tsv)    6210 ms ->  539 ms
render 15 posts      1089 ms ->  313 ms
site tests          29240 ms -> 3020 ms

The long account, with the backend's output, what was changed in the compiler and why, is the post This site is Blimp now.

5In progress: a web framework in Blimp

What is still on Phoenix is chiefly /blinks and its API, which take writes. To move them, the site needs what a framework gives: request bodies, a router with parameters, pipelines of plugs, sessions, CSRF, and rooms with presence. It is being written in Blimp, as ordinary functions over a conn map:

# blimp_site/src/41_web.blimp (blog PR #100, not merged)
def web_demo_routes() -> List do
  [
    web_route("GET", "/web/echo", WEB_BROWSER, web_echo_page),
    web_route("POST", "/web/echo", WEB_BROWSER, web_echo_post),
    web_route("PATCH", "/web/echo/:id", WEB_BROWSER, web_echo_item),
    web_route("DELETE", "/web/echo/:id", WEB_BROWSER, web_echo_item),
    web_route("POST", "/web/api/echo", WEB_API, web_echo_api)
  ]
end

def web_echo_post(conn: Map) -> Map do
  count = web_or(web_get_session(conn, "count"), 0) + 1
  message = web_or(web_param(conn, "message"), "")
  c = web_put_session(web_put_session(conn, "count", count), "last", to_string(message))
  # ... answers JSON or redirects, depending on the request's content type

WEB_BROWSER is [web_fetch_session, web_protect_from_forgery]; WEB_API is [web_fetch_session, web_require_json].

  • Written, in review: bodies read to Content-Length (1 MiB cap), a router with :params, plug pipelines, HMAC-signed cookie sessions and CSRF tokens (blog #100).
  • Also in review: rooms with presence, one queued flush per tick (blog #102), and a read-only /blinks served by Blimp at /blinks-next, 20 of 27 API fixtures byte-identical to production (blog #103).
  • Planned: the rest of /blinks: writes, the iOS app's comment room, push, and the cutover (blog #99).

The framework's own documentation is at /web/.

6What does not work yet

Each of these was hit by a port of a page and probed, by that port or again for this page.

  • A handler that raises leaves its client waiting. The language has try do ... catch e do ... end, and it catches an error raised inside an actor's handler (a <- :crash where the handler divides by zero gives division_by_zero). The site's request path does not use it yet. --serve logs the failed tick and keeps running, but the request that tick was answering never gets a response (found by the web framework port).
  • Strings are bytes. length("❤️") is 6, and slice can cut a character in half.
  • No P-256 or AES-GCM. ecdh_p256 is an unknown function, so Web Push payloads cannot be encrypted in Blimp. HKDF built from hmac_sha256 does pass RFC 5869.
  • http_start has no timeout, so a remote that never answers holds one of the 32 slots. It stops after 3 redirects, and http_result returns no response headers.
  • No HTTP/2, so Apple push (APNs) cannot be reached.
  • The server is one thread. A client that reads slowly can stall every other request for up to 10 s, so production's Caddy buffers the multi-megabyte files.
  • Actors are never collected. A Temper class compiles to an actor, so Temper Snake adds about 500 permanent actors a frame.
  • The server's random is unseeded. It gives the same sequence after every restart unless a program seeds it from random_bytes.
  • Phoenix still answers some pages. /blinks, /api/blinks and /python-demo come back with Phoenix's headers today.
