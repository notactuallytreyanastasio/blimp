A web framework in Blimp: routes, bodies, sessions, CSRF

Until this chapter, the Blimp server behind bobbby.online read each request with one read(2) of at most 64 KiB that does not wait, and answered every method except GET and HEAD with 405. Nothing could be posted to it. /blinks saves links, comments and reactions, so it could not move off Phoenix.

src/41_web.blimp is the request side of a web framework, written in Blimp. It reads a body to its Content-Length. It routes any method to a pattern with :params and runs a pipeline of plugs before the handler. The session lives in an HMAC-signed cookie, and on a browser route anything that is not a GET or HEAD must carry a CSRF token. The file is 877 lines and has 20 tests. Every transcript on this page comes from a local server built from that branch, after the six fixes described below.

A whole app: a form, a plug, a :param, a JSON API#

This is a notes page. The notes are kept in the session cookie, so it needs no database. It has four routes:

  • a page with a form, which carries the CSRF token in a hidden field
  • the form's POST, behind a plug of its own that refuses a fourth note
  • a GET with a :n path parameter that answers JSON
  • a JSON API route that opts out of the token

Blimp has no imports, and the site builds into one file, so this is a file in blimp_site/src/ that sorts after 41_web.blimp.

# notes: a page with a form, a route with a :param, a plug of our own,
# and a JSON API. The notes live in the session cookie.

def notes_routes() -> List do
  [
    web_route("GET", "/notes", WEB_BROWSER, notes_page),
    web_route("POST", "/notes", list_append(WEB_BROWSER, [notes_cap]), notes_add),
    web_route("GET", "/notes/:n", WEB_BROWSER, notes_show),
    web_route("POST", "/api/notes", WEB_API, notes_api)
  ]
end

def notes_of(conn: Map) -> List do
  web_or(web_get_session(conn, "notes"), [])
end

# A plug: refuse a fourth note, and stop the pipeline.
def notes_cap(conn: Map) -> Map do
  case length(notes_of(conn)) >= 3 do
    true -> web_refuse(conn, 422, "three notes is the limit")
    false -> conn
  end
end

def notes_page(conn: Map) -> Map do
  c = web_ensure_csrf(conn)
  items = join(map(notes_of(c), fn(n: String) -> String do
    concat("<li>", escape_html(n), "</li>")
  end), "")
  web_html(c, 200, join([
    "<!doctype html><title>notes</title><ul>", items, "</ul>",
    "<form method=\"post\" action=\"/notes\">",
    "<input type=\"hidden\" name=\"_csrf_token\" value=\"", c.csrf_token, "\">",
    "<input name=\"text\"> <button>Add</button></form>"
  ], ""))
end

def notes_add(conn: Map) -> Map do
  text = web_or(web_param(conn, "text"), "")
  case text do
    "" -> web_refuse(conn, 422, "a note needs text")
    _ -> web_redirect(web_put_session(conn, "notes", list_append(notes_of(conn), [text])), "/notes")
  end
end

def notes_show(conn: Map) -> Map do
  notes = notes_of(conn)
  n = to_int(web_param(conn, "n"))
  case n >= 1 and n <= length(notes) do
    true -> web_json(conn, 200, %{n: n, text: elem_at(notes, n - 1)})
    false -> web_json(conn, 404, %{error: "no such note"})
  end
end

def notes_api(conn: Map) -> Map do
  text = lookup(conn.body_params, "text")
  case type_of(text) == :string do
    true -> web_json(conn, 201, %{saved: text, words: length(split(text, " "))})
    false -> web_json(conn, 422, %{error: "send {\"text\": \"...\"}"})
  end
end

Some things in it that are easy to miss:

  • A named def is a function value. notes_page goes into the route as it is. You can also write fn(c: Map) -> Map do ... end inline.
  • A pipeline is a plain list. list_append(WEB_BROWSER, [notes_cap]) is the browser pipeline with one more plug on the end. WEB_BROWSER is [web_fetch_session, web_protect_from_forgery], so the token is checked before notes_cap runs.
  • web_refuse writes the response and halts. No later plug runs, and neither does the handler.
  • The conn is immutable. Every helper returns a new one. web_ensure_csrf(conn) returns a conn whose csrf_token is set, and the page has to use that conn (c). If it used the old one, the page would render with an empty token and the new session would never be saved.
  • The session holds JSON. A list of strings is fine. An atom or a tuple does not survive the round trip.

Wiring it into the server#

Routes are registered in one list, WEB_ROUTES, at boot in main.blimp. The PR sets it to the demo routes. To add yours, change that line:

# main.blimp, after `routes = stack_routes(routes)`
WEB_ROUTES = list_append(web_demo_routes(), notes_routes())
WEB_SECRET = web_session_secret()

From then on, handle() sends a request to the framework in two cases:

  • Any method but GET and HEAD: always, and first. The prebuilt pages and dynamic() answer only GET and HEAD, so nothing else is asked. If no route matches, the answer is 405 with Allow: GET, HEAD, which is what every POST got before. That holds whatever the body looks like: a chunked POST to /blog is 405, not 411. Body framing (411, 413, 408, 431) is judged only for a request a route will hand to a handler.
  • A GET or HEAD for a path that is not one of the site's prebuilt pages is checked against WEB_ROUTES before dynamic(). Only a GET route claims it. web_handle returns nil when no GET route matches that path, and the request goes on to dynamic() the same as before.

So a POST route can sit beside a page that dynamic() serves. With POST /directory registered, GET /directory is still the directory page. The one thing that is wrong there is the 405 for a third method: its Allow lists POST and not the GET and HEAD that dynamic() answers, because the framework cannot know what dynamic() serves without running it. See routing.

The JSON API

The WEB_API pipeline takes no token. It takes only Content-Type: application/json, and a form is 415. The reason is on the reference page: a cross-site form cannot send that content type.

Anyone can read a session

The cookie is signed, not encrypted. The part before the dot is base64url JSON:

$ COOKIE=$(grep _blimp_session jar | awk '{print $7}')
$ python3 -c 'import base64,sys; p=sys.argv[1].split(".")[0]; print(base64.urlsafe_b64decode(p+"="*(-len(p)%4)).decode())' "$COOKIE"
{"_csrf_token":"KQ2xpws8tvDmEDufEexAs4Lh_GbO5HENDdsNzQ_y7Sc","notes":["buy milk & eggs","two","three"]}

That is why a session should hold ids, not secrets. Change a byte and the MAC fails. The session is then dropped, the server logs a line, and the request runs with no session, so its CSRF check fails with a 403.

In a browser#

The same flow in headless Chrome: read the hidden token out of the page, fetch() a form POST, then read the list.

http://127.0.0.1:4176/notes  200 | <ul><li>from chrome</li></ul>
http://localhost:4176/notes  200 | <ul><li>from chrome</li></ul>
http://192.168.1.238:4176/notes  200 | <ul><li>from chrome</li></ul>

The third line is the machine's LAN address, the one a phone on the same wifi would use, and it used to be a 403. The cookie used to be Secure everywhere, and a browser keeps a Secure cookie over plain HTTP only from localhost. From a LAN address the session never came back, so there was no token, so every form POST failed its CSRF check. The cookie is now Secure only when DATABASE_URL is set, the same test the site uses to decide it is production. Production is behind Caddy, which serves HTTPS, and there the cookie is still Secure (sessions).

What happens to one request#

  1. Read. For anything but GET and HEAD, web_read_rest keeps reading until it has the headers and Content-Length bytes of body, for up to 2 seconds. It answers Expect: 100-continue on the way.
  2. Route. The first route whose pattern and method match wins. A GET or HEAD is claimed only by a GET route, and otherwise falls through to dynamic(). Any other method with no route for it gets 405 with Allow, before its body is looked at.
  3. Frame. A request a route matched is refused before the handler sees it for: a header block over 16 KiB, whether it is still arriving or came whole (431), a chunked body (411), a Content-Length that is not a number (400), a body over 1 MiB (413, not read), and a body that did not all arrive (408).
  4. Conn. The request becomes a map: headers, cookies, query, and the body, which is exactly Content-Length bytes (empty when there is no Content-Length), parsed by its content type. A form or a JSON object becomes body_params. Bad JSON is 400, multipart is 415.
  5. Pipeline. The plugs run in order, and one that sets halted ends the pipeline.
  6. Handler. It runs if nothing halted. If a plug or the handler crashes, the answer is a plain 500 internal server error and the log gets one line naming the request.
  7. Finish. The conn becomes bytes. If the session changed, it is re-signed into Set-Cookie. A header value with a CR or LF is a 500, not a split response. A session cookie over 4000 bytes is also a 500. So is a conn that cannot be turned into bytes at all, such as one whose body is nil.

What does not work#

Each item below was checked against the running server.

A crash outside the framework still hangs the client. The framework now catches what its own routes do (below). A runtime error in dynamic() or in one of the prebuilt routes is not caught. It unwinds the server's tick as it did before this chapter: the client waits until it gives up, and the socket stays in CLOSE_WAIT. Only code that 41_web.blimp calls is wrapped.
  • No multipart, so no file uploads. A multipart/* body is refused with 415 "multipart bodies are not supported" before the pipeline runs.
  • No chunked request bodies. They get 411. Clients that stream a body without a length must buffer it and send Content-Length.
  • Sessions never expire. The cookie has no Max-Age, and the signed payload has no timestamp. A copied cookie is valid until SESSION_SECRET changes, and changing it logs everyone out.
  • The CSRF token is not masked. The same 43 characters appear in every page for the life of the session. That makes it readable by a BREACH-style compression attack if the page is ever served compressed next to attacker-controlled text. Phoenix masks the token per render. This does not.
  • One thread. The server answers one connection at a time. A POST whose body is slow holds everyone else for up to 2 seconds. With a client that sent its headers and then 7 of 20 body bytes, a GET made at the same moment took 1.79 s to answer. Then the slow client got 408 the body did not all arrive.
  • Allow can be short. A path with a web route for POST and a dynamic() page for GET answers PUT with 405 Allow: POST. The GET and HEAD are missing because only dynamic() knows about them.
  • The 16 KiB header limit covers only requests a route here matches. A 405 is not held to it. A GET that goes on to a prebuilt page or dynamic() is read once, at most 64 KiB, as before: a 17,000-byte header on GET /directory is a 200, and on GET /notes a 431.
  • HEAD runs the GET handler. Side effects happen. HEAD /notes with no cookie creates a session and returns its Set-Cookie.
  • No 404 for an unknown path on POST. A POST to a path no route knows is 405 Allow: GET, HEAD, as it was before this chapter, with or without a Content-Length.
  • No response streaming, no WebSocket routes. A handler returns the whole body. WebSockets still go through the server's existing upgrade() path. They are not part of this.

Fixed since the first draft of this page#

The first version of this page listed six bugs, and later passes found three more: one of the fixes made an empty POST to any path a 411, a + in a path became a space, and the same fix still refused a bodiless POST to a route that takes POST, which HTTP allows. PR #100 now has a commit for each, with a test that fails before it. Each is re-run here against the fixed build.

A handler that crashes answers 500. It used to leave the client waiting and the socket in CLOSE_WAIT. The obvious fix, a try around the handler, is not enough. A handler that returns a conn whose body is nil returns normally, and the failure comes later, when the conn is turned into bytes. So the framework has two try blocks: one around the pipeline and handler, one around building the response. These are two probe routes. One divides 100 by ?n=, and the other answers web_text(conn, 200, head([])), which is nil:

def crash_handler(conn: Map) -> Map do
  n = to_int(web_or(web_param(conn, "n"), "0"))
  web_text(conn, 200, to_string(100 / n))
end
def nil_handler(conn: Map) -> Map do
  web_text(conn, 200, head([]))
end

The body says nothing about the server. Blimp's catch gets an atom with no source location, so the log line names the request, not a file and line. The nil body failed inside web_text here, so it is reported as the handler's crash.

A POST route no longer takes the GET for its path away from dynamic(). GET /directory with POST /directory registered used to be 405. It is the directory page again. The transcript is under routing.

The body is exactly Content-Length bytes. Extra bytes used to stay in the body and could make valid JSON fail to parse. A POST with no length used to take whatever the first read returned. Now the extra bytes are dropped. This fix also made a POST, PUT or PATCH with no length a 411, and that part was wrong; see the last fix below (reading bodies).

431 holds for a complete header block. A 17,000-byte header that arrived in one read used to be accepted (refusals).

The cookie is Secure only in production, so a LAN address over plain HTTP keeps its session (in a browser).

A method the path does not take is 405 before its body is judged (2d5dfbd). The body fix above made framing run before routing, so an empty curl -X POST or -X PUT to any path, /blog included, became 411 where it had been 405. Now the route is found first. Chunked is still 411 and a declared 2 MB body still 413 without being read, on routes that take them (refusals). GET pages are byte-identical to origin/main's build for the 14 paths checked.

A + in a path segment is a + (5d4d55b, found by the blinks writes chapter). Path parameters were form-decoded, so the tag c++ arrived as "c ". Re-run at 5d4d55b, a CSRF-carrying PATCH to the demo:

{"method":"PATCH","id":"c++","params":{"q":"a b","id":"c++"}}
# at 2d5dfbd: {"method":"PATCH","id":"c  ","params":{"q":"a b","id":"c  "}}

A request with no Content-Length has an empty body (d522c8d, found by the Blinks comments chapter's parity run against Phoenix). The body fix made a POST, PUT or PATCH with no length a 411 on a route that takes it. HTTP says otherwise: with neither Content-Length nor Transfer-Encoding, the body has length zero (RFC 9112 §6.3). And the iOS app reports a comment with exactly that, a POST with no body, which Phoenix answers 200 and this answered 411. Now the handler runs with an empty body, and 411 is only for Transfer-Encoding. Bytes after the head of such a request would be the next request, and with no keep-alive they are dropped unread. Re-run at d522c8d (at 5d4d55b both were 411 a body needs a Content-Length):

$ curl -si -X POST -H 'Content-Type: application/json' localhost:4181/web/api/echo | sed -n '1p;$p'
HTTP/1.1 200 OK
{"json":null,"session":"none"}
$ curl -s -b jar -X PATCH -H "x-csrf-token: $TOKEN" 'localhost:4181/web/echo/c++?q=a+b'     # no Content-Length: 0 needed now
{"method":"PATCH","id":"c++","params":{"q":"a b","id":"c++"}}

The boot refusals print plainly. They used print(), which quotes a string the way source code writes it (SESSION_SECRET).

Rooms and presence (chapter 61)#

The push side lives in PR #102, which is open and not merged. src/89_rooms.blimp is one actor that knows who is in each topic and what every WebSocket is owed. It writes each socket once per tick, and it sends presence as batched diffs keyed by ref. It is separate from this file: sockets still arrive through upgrade(). The rooms page has its API and wire format. It also has the part that does not work yet. A peer that stops reading can still block the only thread for over 10 seconds, because the runtime has no non-blocking write.
