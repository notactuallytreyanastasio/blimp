A web framework in Blimp: routes, bodies, sessions, CSRF

Until this chapter, the Blimp server behind bobbby.online read each request with one read(2) of at most 64 KiB that does not wait, and answered every method except GET and HEAD with 405. Nothing could be posted to it. /blinks saves links, comments and reactions, so it could not move off Phoenix.

src/41_web.blimp is the request side of a web framework, written in Blimp. It reads a body to its Content-Length. It routes any method to a pattern with :params and runs a pipeline of plugs before the handler. The session lives in an HMAC-signed cookie, and on a browser route anything that is not a GET or HEAD must carry a CSRF token. The file is 788 lines and has 15 tests. Every transcript on this page comes from a local server built from that branch.

Where it lives
The site repo, not this one: notactuallytreyanastasio/blog#100, branch blimp-blog/60-web-core, files blimp_site/src/41_web.blimp, blimp_site/test/web_test.blimp, and the hooks in blimp_site/main.blimp. Documented at commit c18668d.

A whole app: a form, a plug, a :param, a JSON API#

This is a notes page. The notes are kept in the session cookie, so it needs no database. It has four routes:

  • a page with a form, which carries the CSRF token in a hidden field
  • the form's POST, behind a plug of its own that refuses a fourth note
  • a GET with a :n path parameter that answers JSON
  • a JSON API route that opts out of the token

Blimp has no imports, and the site builds into one file, so this is a file in blimp_site/src/ that sorts after 41_web.blimp.

# notes: a page with a form, a route with a :param, a plug of our own,
# and a JSON API. The notes live in the session cookie.

def notes_routes() -> List do
  [
    web_route("GET", "/notes", WEB_BROWSER, notes_page),
    web_route("POST", "/notes", list_append(WEB_BROWSER, [notes_cap]), notes_add),
    web_route("GET", "/notes/:n", WEB_BROWSER, notes_show),
    web_route("POST", "/api/notes", WEB_API, notes_api)
  ]
end

def notes_of(conn: Map) -> List do
  web_or(web_get_session(conn, "notes"), [])
end

# A plug: refuse a fourth note, and stop the pipeline.
def notes_cap(conn: Map) -> Map do
  case length(notes_of(conn)) >= 3 do
    true -> web_refuse(conn, 422, "three notes is the limit")
    false -> conn
  end
end

def notes_page(conn: Map) -> Map do
  c = web_ensure_csrf(conn)
  items = join(map(notes_of(c), fn(n: String) -> String do
    concat("<li>", escape_html(n), "</li>")
  end), "")
  web_html(c, 200, join([
    "<!doctype html><title>notes</title><ul>", items, "</ul>",
    "<form method=\"post\" action=\"/notes\">",
    "<input type=\"hidden\" name=\"_csrf_token\" value=\"", c.csrf_token, "\">",
    "<input name=\"text\"> <button>Add</button></form>"
  ], ""))
end

def notes_add(conn: Map) -> Map do
  text = web_or(web_param(conn, "text"), "")
  case text do
    "" -> web_refuse(conn, 422, "a note needs text")
    _ -> web_redirect(web_put_session(conn, "notes", list_append(notes_of(conn), [text])), "/notes")
  end
end

def notes_show(conn: Map) -> Map do
  notes = notes_of(conn)
  n = to_int(web_param(conn, "n"))
  case n >= 1 and n <= length(notes) do
    true -> web_json(conn, 200, %{n: n, text: elem_at(notes, n - 1)})
    false -> web_json(conn, 404, %{error: "no such note"})
  end
end

def notes_api(conn: Map) -> Map do
  text = lookup(conn.body_params, "text")
  case type_of(text) == :string do
    true -> web_json(conn, 201, %{saved: text, words: length(split(text, " "))})
    false -> web_json(conn, 422, %{error: "send {\"text\": \"...\"}"})
  end
end

Some things in it that are easy to miss:

  • A named def is a function value. notes_page goes into the route as it is. You can also write fn(c: Map) -> Map do ... end inline.
  • A pipeline is a plain list. list_append(WEB_BROWSER, [notes_cap]) is the browser pipeline with one more plug on the end. WEB_BROWSER is [web_fetch_session, web_protect_from_forgery], so the token is checked before notes_cap runs.
  • web_refuse writes the response and halts. No later plug runs, and neither does the handler.
  • The conn is immutable. Every helper returns a new one. web_ensure_csrf(conn) returns a conn whose csrf_token is set, and the page has to use that conn (c). If it used the old one, the page would render with an empty token and the new session would never be saved.
  • The session holds JSON. A list of strings is fine. An atom or a tuple does not survive the round trip.

Wiring it into the server#

Routes are registered in one list, WEB_ROUTES, at boot in main.blimp. The PR sets it to the demo routes. To add yours, change that line:

# main.blimp, after `routes = stack_routes(routes)`
WEB_ROUTES = list_append(web_demo_routes(), notes_routes())
WEB_SECRET = web_session_secret()

From then on, handle() sends a request to the framework in two cases:

  • Any method but GET and HEAD: always. If no route matches, the answer is 405 with Allow: GET, HEAD, which is what every POST got before.
  • A GET or HEAD for a path that is not one of the site's prebuilt pages is checked against WEB_ROUTES before dynamic(). web_handle returns nil when no route matches that path, and the request goes on to dynamic() the same as before.

A route for any method takes its path away from dynamic(), not only a GET route. The PR's own summary says a web GET route shadows a dynamic path. That is true, but it is not the whole rule. I registered only POST /directory, and GET /directory, a page that dynamic() serves with a 200, became 405 Allow: POST. If a path has a web route for any method, give it the GET route too. See routing.

The JSON API

The WEB_API pipeline takes no token. It takes only Content-Type: application/json, and a form is 415. The reason is on the reference page: a cross-site form cannot send that content type.

Anyone can read a session

The cookie is signed, not encrypted. The part before the dot is base64url JSON:

$ COOKIE=$(grep _blimp_session jar | awk '{print $7}')
$ python3 -c 'import base64,sys; p=sys.argv[1].split(".")[0]; print(base64.urlsafe_b64decode(p+"="*(-len(p)%4)).decode())' "$COOKIE"
{"_csrf_token":"M2vtGUOxzbAPnm0Zw6hwpFOtOw2WpRtpXdKAwvtwaSE","notes":["buy milk & eggs","two","three"]}

That is why a session should hold ids, not secrets. Change a byte and the MAC fails. The session is then dropped, the server logs a line, and the request runs with no session, so its CSRF check fails with a 403.

In a browser#

The same flow in headless Chrome: read the hidden token out of the page, fetch() a form POST, then read the list.

http://127.0.0.1:4170/notes      200 | <ul><li>from chrome</li></ul>
http://localhost:4170/notes      200 | <ul><li>from chrome</li></ul>
http://192.168.1.238:4170/notes  403 | <ul></ul>

The third line is the Secure cookie attribute doing its job. Browsers accept a Secure cookie over plain HTTP only from localhost. From a LAN address there is no cookie, so there is no token, so the POST is a 403. To test from a phone on the same network, go through HTTPS. Production is behind Caddy, which serves HTTPS.

What happens to one request#

  1. Read. For anything but GET and HEAD, web_read_rest keeps reading until it has the headers and Content-Length bytes of body, for up to 2 seconds. It answers Expect: 100-continue on the way.
  2. Frame. Some requests are refused before any route sees them: a chunked body (411), a Content-Length that is not a number (400), a body over 1 MiB (413), 16 KiB of headers with no blank line after them yet (431), and a body that did not all arrive (408).
  3. Route. The first route whose pattern and method match wins. If the path matches only routes for other methods, the answer is 405 with Allow. If nothing matches, a GET falls through to dynamic().
  4. Conn. The request becomes a map: headers, cookies, query, and the body parsed by its content type. A form or a JSON object becomes body_params. Bad JSON is 400, multipart is 415.
  5. Pipeline. The plugs run in order, and one that sets halted ends the pipeline.
  6. Handler. It runs if nothing halted.
  7. Finish. The conn becomes bytes. If the session changed, it is re-signed into Set-Cookie. A header value with a CR or LF is a 500, not a split response. A session cookie over 4000 bytes is also a 500.

What does not work#

Each item below was checked against the running server.

A handler that crashes leaves the client hanging. web_dispatch calls the plugs and the handler with no try around them. A runtime error in either one aborts that tick of the server actor. The interpreter prints the error and its source line to stderr. But the connection is never answered or closed, and the request gets no access-log line. Here is a route whose handler divides by ?n=: 
def crash_handler(conn: Map) -> Map do
  n = to_int(web_or(web_param(conn, "n"), "0"))
  web_text(conn, 200, to_string(100 / n))
end
$ curl -s -w ' (%{http_code})\n' 'localhost:4173/crash?n=4'
25 (200)
$ curl -s -w '%{http_code} after %{time_total}s\n' --max-time 5 'localhost:4173/crash?n=0'
000 after 5.004907s
$ lsof -nP -iTCP:4173 | grep -c CLOSE_WAIT   # after two crashed requests
2
The server goes on answering other requests, but each crash leaks a file descriptor. Blimp does have try ... catch (it catches :division_by_zero, :type_error and the rest), and the framework should wrap the handler in it and answer 500. Until it does, wrap a handler that can fail yourself: 
def crash_safe(conn: Map) -> Map do
  try do
    crash_handler(conn)
  catch e do
    puts(concat("handler failed: ", to_string(e), " on ", conn.method, " ", conn.path))
    web_text(conn, 500, "internal error")
  end
end
$ curl -s -w ' (%{http_code})\n' 'localhost:4173/crash-safe?n=0'
internal error (500)
# server log: handler failed: division_by_zero on GET /crash-safe
That try does not cover what happens after the handler returns. head([]) is nil in Blimp, not an error. So web_text(conn, 200, head([])) returns normally, and the request then fails inside web_dispatch (I can't use `body` with Nil on the left and String on the right), which hangs the client the same way.
  • No multipart, so no file uploads. A multipart/* body is refused with 415 "multipart bodies are not supported" before the pipeline runs.
  • No chunked request bodies. They get 411. Clients that stream a body without a length must buffer it and send Content-Length.
  • Sessions never expire. The cookie has no Max-Age, and the signed payload has no timestamp. A copied cookie is valid until SESSION_SECRET changes, and changing it logs everyone out.
  • The CSRF token is not masked. The same 43 characters appear in every page for the life of the session. That makes it readable by a BREACH-style compression attack if the page is ever served compressed next to attacker-controlled text. Phoenix masks the token per render. This does not.
  • One thread. The server answers one connection at a time. A POST whose body is slow holds everyone else for up to 2 seconds. With a client that sent its headers and then 7 of 20 body bytes, a GET made at the same moment took 1.79 s to answer. Then the slow client got 408 the body did not all arrive.
  • Framing is lenient. Bytes after Content-Length are kept in the body: with Content-Length: 14 and 21 bytes sent, the JSON parser saw all 21 and returned a 400. A POST with no Content-Length at all takes whatever arrived in the first read as its body, where HTTP says it has none.
  • A route claims its path for every method. See above.
  • HEAD runs the GET handler. Side effects happen. HEAD /notes with no cookie creates a session and returns its Set-Cookie.
  • No 404 for an unknown path on POST. A POST to a path no route knows is 405 Allow: GET, HEAD, as it was before this chapter.
  • No response streaming, no WebSocket routes. A handler returns the whole body. WebSockets still go through the server's existing upgrade() path. They are not part of this.

Rooms and presence (chapter 61)#

The push side lives in PR #102, which is open and not merged. src/89_rooms.blimp is one actor that knows who is in each topic and what every WebSocket is owed. It writes each socket once per tick, and it sends presence as batched diffs keyed by ref. It is separate from this file: sockets still arrive through upgrade().
