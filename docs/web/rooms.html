Rooms and presence: one actor, one write per socket per tick, and none of them waits

Six live pages on the Blimp server each wrote their own room: a map of sockets to people, a join that sends the newcomer the room, a leave, and a loop over tcp_write. None of them could say who was in a room without code of its own for it. src/89_rooms.blimp does that job once, as an actor. It plays the part of Phoenix's PubSub, Presence and Channel, which is what /blinks uses for the same job.

Where it lives
notactuallytreyanastasio/blog#102, branch blimp-blog/61-rooms, commit 7679339: blimp_site/src/89_rooms.blimp and test/rooms_test.blimp (18 tests, all passing when I ran them).
Needs Blimp #73 (tcp_write_some, branch 35-io-nonblocking) in the interpreter that runs it. On one without it, the first flush that has something to write stops with UNKNOWN FUNCTION tcp_write_some.
Open PR, not merged or deployed. /cursor-tracker is the one page moved onto it so far. MAP_ROOM, FIREHOSE, MTA, BJ and WORDLE still keep their own loops.
How it relates to the request side
It is separate. WebSockets still arrive through the server's existing upgrade(), and the hub is given their fds. It never parses a frame the client sends. The app does that and asks the hub whether it may act on it.

The shape#

The site has one hub, ROOMS = spawn Rooms, and a test spawns its own. A topic is a room: "cursors", "blink:42". A socket is a plain fd. Nothing is written when it is said. :broadcast frames the text once and puts it on an outbox. main.blimp's live_tick calls ROOMS <- :flush once per tick, after every room has pushed, and each socket then gets everything addressed to it that tick in one tcp_write_some. That call takes what the kernel has room for and returns at once. Whatever it does not take becomes the socket's backlog, which goes out first at the next flush (see a socket that stops reading). Sockets in the same set of topics share one built string.

messagereplywhat it does
:open(topic, %{diffs: Bool, format: fn}):okOptional. A topic opens itself on first join with diffs: true. format is fn(event: String, topic: String, body: Map) -> String and shapes the presence frames. Opening a topic that is already open changes only the options given. To go back to the default frames, pass format: rooms_format.
:join(topic, fd, who, meta)memberAdds fd as who. Joining again replaces the old membership. With diffs on, the joiner is queued a presence_state.
:update(topic, fd, meta)member or nilReplaces meta. Returns nil when fd is not in the topic.
:patch(topic, fd, fields)member or nilMerges fields into meta.
:leave(topic, fd):ok
:drop(fd)topics leftThe socket is gone, so it leaves every topic. Everything queued for it alone (its presence_state, a :send) comes off the outbox, joined or not, and so does any backlog it still owes. Call it whenever you close an fd the hub has written to. main.blimp's drop_socket does this for every WebSocket.
:member(topic, fd) / :list(topic)member or nil / members:list gives members in join order.
:broadcast(topic, text):okQueues text for every member of the topic.
:broadcast_from(fd, topic, text):okThe same, except for fd.
:send(fd, text):okOne socket, whether it has joined a topic or not. A socket in no topic is written at the next flush and is not added to any topic. A :drop before that flush takes it back.
:inbound(fd):ok or :limitedCall it for every frame received. On :limited, drop the frame.
:flush%{sockets, frames, bytes, kicked, written, owed, behind}Writes everything queued, plus whatever earlier flushes still owe, and never waits. written is the number of bytes the kernel took, owed the backlog left over, and behind how many sockets carry one. Close each fd in kicked.
:flush_at(t)the sameA flush at time t (ms), so a test can reach the stall bound without waiting 10 s.

A member is %{ref, who, since, meta}. The app chooses who. ref is made at join and survives updates. since is now_ms() at join, the interpreter's millisecond clock (407866824 in the run below). It is not a Unix time, so do not show it as a date.

The two flush lines are from 7679339. The rest of this run is from 9c188a5; 7679339 gives the same counts. Test sockets are never written, so written, owed and behind are always 0 for them.

  • Presence is batched. There is one presence_diff per topic per flush, not one per event. Two joins in one tick arrive as one frame.
  • Apply leaves, then joins, keyed by ref. An update is sent as the member's old self in leaves and new self in joins, with the same ref. A member who came and went within one tick, cy here, is in neither list, and nobody else sees them. cy is not written either: its :leave took back the presence_state its join had queued (9c188a5). At 78e9b3f cy was still sent that state, which listed cy as a member, and the flush above was {"sockets":3,"frames":4,"bytes":714}.
  • A joiner's presence_state and the diff after it overlap. bob's state already lists ada and bob, and the diff lists them again. Keying by ref makes the overlap harmless.
  • App frames are sent exactly as given. The hub adds nothing to them, so an existing page keeps its own protocol.
  • diffs: false turns off presence_state and presence_diff entirely, and a later :open that does not name diffs leaves it off. /cursor-tracker uses it because its own "users" frame already carries the room. It builds that frame from :list.
  • format is for a client that wants another shape. The iOS blinks app speaks Phoenix v2, [join_ref, ref, topic, event, payload], and a test covers a v2 formatter. It survives a second :open that does not name it: 
    hub <- :open("t", %{format: v2})
hub <- :open("t", %{})
hub <- :join("t", -9, "eve", %{})

hub <- :sent(-9)
    [null,null,"t","presence_state",{"members":[{"ref":"-9.5","who":"eve","since":407866825,"meta":{}}]}]
    Before 2a4ef58 that frame was {"t":"presence_state",...}, the default shape.
  • :send reaches a socket that has joined nothing. A page can be told who it is, or why it was refused, before it joins: 
    hub <- :send(-7, "{\"t\":\"hello\"}")

  • A :drop takes back what was queued for the socket; a :leave, what was queued for it in that topic. The :send fix brought a bug with it, found while writing this page: :join queues a presence_state addressed to the joiner, :drop left it in the outbox, and the flush now delivers an addressed entry to any fd, so a socket dropped in the tick it joined was written after its connection had closed: a closed fd, or a new connection the kernel gave the same number. Bounds#

  • Inbound: a token bucket per socket, ROOMS_RATE = 30 frames a second with bursts of ROOMS_BURST = 60. Seventy frames at the same instant: 
    ok: 60, limited: 10
  • Backlog: a socket that owes more than ROOMS_MAX_BYTES (262144) after the kernel has taken its share is kicked. It leaves every topic, and its fd comes back in kicked for main.blimp to close. The hub does not drop frames and carry on, because the page would then show a room that is not the room.
  • Stall: a socket is kicked the same way when its backlog has had no byte taken for ROOMS_STALL_MS (10000). The clock runs from the last byte the kernel took, so a reader that is slow but still reading is never kicked for it. 10 s is the no-progress limit tcp_write already had, so no page that survived before is kicked now. The bound exists for a quiet room, where a phone that has gone to sleep would take hours to owe 256 KB.
  • Gone: when tcp_write_some answers :error (EPIPE, ECONNRESET), the socket is kicked.

A socket that stops reading#

Before 7679339 this was the first item under "What does not work". tcp_write either takes all of its data or blocks the only thread until 10 s pass with nothing taken, so one page that stopped reading stopped the whole site. Blimp #73 added tcp_write_some(fd, data) -> Int | :error, and :flush now makes exactly one such call per socket. The data is the socket's backlog followed by this tick's frames. The kernel takes what fits, and the rest stays owed, ahead of anything newer. Bytes therefore leave in the order they were said. A frame can be split only between two writes to the same socket, and a WebSocket reader cannot tell that apart from TCP splitting it.

The PR's probe, which I re-ran: one hub broadcasts 64 KB per tick to two members, one of which never reads. Once that member owes anything, the broadcast drops to 1 KB per tick so that it stays in the room for a while. A client asks for a page every 20 ms for 6 s. Both runs use the #73 interpreter; only the rooms file differs.

The other side is the page. I paused /cursor-tracker's JavaScript under the debugger in headless Chrome, so Chrome stopped reading, and sent it 30 frames of 30 KB through the control socket. From frame 27 on, the socket owed 3172, 33204, 63236 and 93268 bytes, so frame 27 went out in two pieces. After resuming:

page received 30 blob frames; every one whole and in order: true
B after its own click: Point 1: X:50 Y:39 by you | 1 user(s) online

Two things you might expect it to do, and why it does not:

  • It does not ask tcp_poll_write first. On macOS the answer was wrong in both directions. Writing 64 KB at a time to a peer that never read, poll said "not writable" twice, and the next send took 32664 and 65536 bytes. A send that takes 0 costs about 1.3 µs, so each socket that owes gets one send per flush, and the flush never loops on "writable".
  • A backlog does not outlive its fd. A backlog left behind for a closed fd would be written to a closed descriptor, which raises a TypeError and stops the flush, or to whichever connection the kernel hands that number next. :drop forgets it. /cursor-tracker only ever called :leave on close, so main.blimp now calls :drop for every WebSocket it closes.

What does not work#

  • It costs more than the hand-written loop it replaces. The PR measured about 1.8 times the cursor room's old tick: 1450 µs against 2575 µs at 100 visitors. A move is now two hub calls instead of one put. When everyone joins in the same tick, presence is quadratic, because each joiner's state lists everyone before it: 250 joins took 45 ms, and their flush 44 ms. I did not re-run those. I did re-run the tick bench for the non-blocking flush: 9c188a5 against 7679339, median of 5 runs each, in µs per tick. It came out 350/1750/3725/10725 before and 400/1825/3875/11125 after at 10/50/100/250 visitors, about 4% at 50 and above. The flush alone went up about 20%.
  • The limits are global constants. There is no per-topic or per-socket rate.
  • Nothing live has exercised the kick through main.blimp. A paused cursors tab could now reach it by owing 256 KB or by stalling for 10 s, but I did not run that through the site. The hub side is tested against real loopback sockets: a peer that never reads, a backlog that is paid once the peer reads, a kick past the bound, a kick after the stall, and :drop. The close in main.blimp is not tested.
