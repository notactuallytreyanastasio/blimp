Rooms and presence: one actor, one write per socket per tick

Six live pages on the Blimp server each wrote their own room: a map of sockets to people, a join that sends the newcomer the room, a leave, and a loop over tcp_write. None of them could say who was in a room without code of its own for it. src/89_rooms.blimp does that job once, as an actor. It plays the part of Phoenix's PubSub, Presence and Channel, which is what /blinks uses for the same job.

Where it lives
notactuallytreyanastasio/blog#102, branch blimp-blog/61-rooms, commit 9c188a5: blimp_site/src/89_rooms.blimp and test/rooms_test.blimp (13 tests, all passing when I ran them).
Open PR, not merged or deployed. /cursor-tracker is the one page moved onto it so far. MAP_ROOM, FIREHOSE, MTA, BJ and WORDLE still keep their own loops.
How it relates to the request side
It is separate. WebSockets still arrive through the server's existing upgrade(), and the hub is given their fds. It never parses a frame the client sends. The app does that and asks the hub whether it may act on it.

The shape#

The site has one hub, ROOMS = spawn Rooms, and a test spawns its own. A topic is a room: "cursors", "blink:42". A socket is a plain fd. Nothing is written when it is said. :broadcast frames the text once and puts it on an outbox. main.blimp's live_tick calls ROOMS <- :flush once per tick, after every room has pushed, and each socket then gets everything addressed to it that tick in one tcp_write. Sockets in the same set of topics share one built string.

messagereplywhat it does
:open(topic, %{diffs: Bool, format: fn}):okOptional. A topic opens itself on first join with diffs: true. format is fn(event: String, topic: String, body: Map) -> String and shapes the presence frames. Opening a topic that is already open changes only the options given. To go back to the default frames, pass format: rooms_format.
:join(topic, fd, who, meta)memberAdds fd as who. Joining again replaces the old membership. With diffs on, the joiner is queued a presence_state.
:update(topic, fd, meta)member or nilReplaces meta. Returns nil when fd is not in the topic.
:patch(topic, fd, fields)member or nilMerges fields into meta.
:leave(topic, fd):ok
:drop(fd)topics leftThe socket is gone, so it leaves every topic, and everything queued for it alone (its presence_state, a :send) is taken off the outbox, joined or not.
:member(topic, fd) / :list(topic)member or nil / members:list gives members in join order.
:broadcast(topic, text):okQueues text for every member of the topic.
:broadcast_from(fd, topic, text):okThe same, except for fd.
:send(fd, text):okOne socket, whether it has joined a topic or not. A socket in no topic is written at the next flush and is not added to any topic. A :drop before that flush takes it back.
:inbound(fd):ok or :limitedCall it for every frame received. On :limited, drop the frame.
:flush%{sockets, frames, bytes, kicked}Writes everything queued. Close each fd in kicked.
:sent(fd) / :statstexts / map:sent is for tests: a negative fd is never written, and this returns what it would have been sent.

A member is %{ref, who, since, meta}. The app chooses who. ref is made at join and survives updates. since is now_ms() at join, the interpreter's millisecond clock (407866824 in the run below). It is not a Unix time, so do not show it as a date.

What goes on the wire#

This is real output. Test sockets -1 (ada) and -2 (bob) join "blink:42", and the hub flushes. Then ada broadcasts a comment to everyone but herself and patches her meta. cy joins and leaves within the same tick, and the hub flushes again:

hub = spawn Rooms
hub <- :join("blink:42", -1, "ada", %{name: "Ada"})
hub <- :join("blink:42", -2, "bob", %{name: "Bob"})
hub <- :flush
hub <- :broadcast_from(-1, "blink:42", "{\"t\":\"comment\",\"body\":\"hi\"}")
hub <- :patch("blink:42", -1, %{typing: true})
hub <- :join("blink:42", -3, "cy", %{})
hub <- :leave("blink:42", -3)
hub <- :flush
join   -> {"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada"}}
flush  -> {"sockets":2,"frames":4,"bytes":713,"kicked":[]}
ada <- {"t":"presence_state","topic":"blink:42","members":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada"}}]}
ada <- {"t":"presence_diff","topic":"blink:42","joins":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada"}},{"ref":"-2.2","who":"bob","since":407866825,"meta":{"name":"Bob"}}],"leaves":[]}
bob <- {"t":"presence_state","topic":"blink:42","members":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada"}},{"ref":"-2.2","who":"bob","since":407866825,"meta":{"name":"Bob"}}]}
bob <- {"t":"presence_diff","topic":"blink:42","joins":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada"}},{"ref":"-2.2","who":"bob","since":407866825,"meta":{"name":"Bob"}}],"leaves":[]}
flush  -> {"sockets":2,"frames":3,"bytes":455,"kicked":[]}
ada <- {"t":"presence_diff","topic":"blink:42","joins":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada","typing":true}}],"leaves":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada"}}]}
bob <- {"t":"comment","body":"hi"}
bob <- {"t":"presence_diff","topic":"blink:42","joins":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada","typing":true}}],"leaves":[{"ref":"-1.1","who":"ada","since":407866824,"meta":{"name":"Ada"}}]}
  • Presence is batched. There is one presence_diff per topic per flush, not one per event. Two joins in one tick arrive as one frame.
  • Apply leaves, then joins, keyed by ref. An update is sent as the member's old self in leaves and new self in joins, with the same ref. A member who came and went within one tick, cy here, is in neither list, and nobody else sees them. cy is not written either: its :leave took back the presence_state its join had queued (9c188a5). At 78e9b3f cy was still sent that state, which listed cy as a member, and the flush above was {"sockets":3,"frames":4,"bytes":714}.
  • A joiner's presence_state and the diff after it overlap. bob's state already lists ada and bob, and the diff lists them again. Keying by ref makes the overlap harmless.
  • App frames are sent exactly as given. The hub adds nothing to them, so an existing page keeps its own protocol.
  • diffs: false turns off presence_state and presence_diff entirely, and a later :open that does not name diffs leaves it off. /cursor-tracker uses it because its own "users" frame already carries the room. It builds that frame from :list.
  • format is for a client that wants another shape. The iOS blinks app speaks Phoenix v2, [join_ref, ref, topic, event, payload], and a test covers a v2 formatter. It survives a second :open that does not name it: 
    hub <- :open("t", %{format: v2})
hub <- :open("t", %{})
hub <- :join("t", -9, "eve", %{})
hub <- :flush
hub <- :sent(-9)
    [null,null,"t","presence_state",{"members":[{"ref":"-9.5","who":"eve","since":407866825,"meta":{}}]}]
    Before 2a4ef58 that frame was {"t":"presence_state",...}, the default shape.
  • :send reaches a socket that has joined nothing. A page can be told who it is, or why it was refused, before it joins: 
    hub <- :send(-7, "{\"t\":\"hello\"}")
hub <- :flush
hub <- :sent(-7)
(hub <- :stats).sockets
    flush  -> {"sockets":1,"frames":1,"bytes":15,"kicked":[]}
:sent(-7) -> ["{\"t\":\"hello\"}"]
:stats sockets -> [{"fd":-1,"topics":["blink:42"],"limited":0},{"fd":-2,"topics":["blink:42"],"limited":0}]
    -7 got one write and the same 256 KB bound as a member, and it is not in the socket table afterwards: a :send is not a join. Before 78e9b3f that flush wrote nothing and :sent(-7) was [].
  • A :drop takes back what was queued for the socket; a :leave, what was queued for it in that topic. The :send fix brought a bug with it, found while writing this page: :join queues a presence_state addressed to the joiner, :drop left it in the outbox, and the flush now delivers an addressed entry to any fd, so a socket dropped in the tick it joined was written after its connection had closed: a closed fd, or a new connection the kernel gave the same number. Fixed in 9c188a5. The same run at 78e9b3f and at 9c188a5, after ada and bob have joined and flushed: 
    hub <- :join("blink:42", -4, "dan", %{})
hub <- :drop(-4)
hub <- :flush
hub <- :sent(-4)
    # 78e9b3f
:drop(-4) -> ["blink:42"]
flush  -> {"sockets":1,"frames":1,"bytes":246,"kicked":[]}
:sent(-4) -> ["{\"t\":\"presence_state\",\"topic\":\"blink:42\",\"members\":[...ada, bob, dan...]}"]
# 9c188a5
:drop(-4) -> ["blink:42"]
flush  -> {"sockets":0,"frames":0,"bytes":0,"kicked":[]}
:sent(-4) -> []
    A :leave is not a close, so it takes back less: only the entries for fd in the topic it left. The frames queued for its other topics, and a :send, still go out, and a socket that leaves its last topic can still be sent to. eve joins two topics, is sent a hello, and leaves one of them in the same tick: 
    hub <- :join("blink:42", -5, "eve", %{})
hub <- :join("lobby", -5, "eve", %{})
hub <- :send(-5, "{\"t\":\"hello\"}")
hub <- :leave("blink:42", -5)
hub <- :flush
    # 78e9b3f: the state of the room eve left goes out after the leave
flush  -> {"sockets":1,"frames":4,"bytes":484,"kicked":[]}
eve <- presence_state blink:42, presence_state lobby, hello, presence_diff lobby
# 9c188a5
flush  -> {"sockets":1,"frames":3,"bytes":238,"kicked":[]}
eve <- presence_state lobby, hello, presence_diff lobby
    The test that covers both failed at 78e9b3f with left: 1, right: 0 (the sockets the flush wrote) and passes at 9c188a5.

Bounds#

  • Inbound: a token bucket per socket, ROOMS_RATE = 30 frames a second with bursts of ROOMS_BURST = 60. Seventy frames at the same instant: 
    ok: 60, limited: 10
  • Outbound: a socket owed more than ROOMS_MAX_BYTES (262144) in one flush is not written. It leaves every topic, and its fd comes back in kicked for main.blimp to close. The hub does not drop frames and carry on, because the page would then show a room that is not the room.

What does not work#

A slow reader can still stop the whole site. tcp_write either takes all of its data or blocks the only thread until 10 s pass with nothing taken. tcp_poll reports only readability, and the runtime has no write that takes what fits and returns. The PR's probe connects a peer that never reads, and here is my run of it: 
"64KB: ok in 0ms"
"64KB more: ok in 0ms"
"4MB more: error in 15117ms"
"FAIL: tcp_write blocked the only thread; there is no write that takes what fits and returns (wanted: tcp_write_some(fd, data) -> bytes taken, or tcp_poll reporting writability)"
The PR measured 20.3 s for the same write. The 256 KB bound only limits how much one tick adds to a stalled socket's backlog. The PR reports that loopback absorbs about 768 KB before the first write blocks. The fix needs a runtime primitive, tcp_write_some or write interest in tcp_poll, and then :flush is the only place that needs to change. That primitive is being added to the interpreter as I write this, on the Blimp repo's branch 35-io-nonblocking, and the rooms library does not use it yet.
  • It costs more than the hand-written loop it replaces. The PR measured about 1.8 times the cursor room's old tick: 1450 µs against 2575 µs at 100 visitors. A move is now two hub calls instead of one put. When everyone joins in the same tick, presence is quadratic, because each joiner's state lists everyone before it: 250 joins took 45 ms, and their flush 44 ms. I did not re-run these benchmarks.
  • The limits are global constants. There is no per-topic or per-socket rate.
  • Nothing live exercises the kick. A cursor page is never owed 256 KB in one tick. The hub side is tested, but the close in main.blimp is not.
