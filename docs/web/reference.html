The conn#

A request is a map, built by web_conn. Every key is always present. Keys are atoms (conn.method). The maps inside it (headers, params, session) have string keys, so you read them with lookup(conn.headers, "cookie"). There is no field access for those. A plug or handler takes a conn and returns one. To set a field, use put(conn, :cache, "...").

Why web_url_decode exists. The obvious move is to reuse url_decode from src/40_http.blimp, but it recurses once per byte. Blimp's interpreter reclaims nothing until the tick returns, so a 300 KB form field ran it out of its 2 GB heap, and the request was never answered. web_url_decode splits on % and joins natively, one step per %. The test decodes a 512 KiB field with it. On the running server, a 300,012-byte JSON body was parsed and answered in 7 ms:

$ curl -s -w "\n%{http_code} %{time_total}s\n" -H 'Content-Type: application/json' --data-binary @big.json localhost:4170/api/notes | tail -c 60
word word word word word word","words":60000}
201 0.006634s

Routing#

  • Segments match exactly, and :name matches one non-empty segment. /api/blinks/:id/save matches /api/blinks/42/save. It does not match /api/blinks//save, /api/blinks/42 or /api/blinks/42/save/x. A :param is URL-decoded, so /web/echo/a%20b gives id = "a b". There are no wildcards and no optional segments. A trailing slash is a segment of its own, so /notes/ does not match /notes. It falls through to dynamic(), which redirects it.
  • The first match wins, in the order of the WEB_ROUTES list.
  • HEAD is answered by the GET route. The handler runs, and the response has the GET's headers, including its Content-Length, with no body. A handler with side effects has them on HEAD too.
  • 405 with Allow. If the path matches only routes for other methods, the answer is 405. Allow lists those methods, and HEAD is added when there is a GET. OPTIONS is not special. It is a 405 too.
  • Precedence over dynamic(). The prebuilt pages, / and the posts, are answered before the framework is asked. Then, for a GET or HEAD, WEB_ROUTES is checked before dynamic(). If any route of any method matches the path, the framework answers. For other methods it answers with a 405, and dynamic() never sees that path.
$ curl -si -X PUT localhost:4170/notes          # GET and POST routes exist
HTTP/1.1 405 Method Not Allowed
Allow: GET, POST, HEAD
$ curl -si -X DELETE localhost:4170/notes/1      # only GET /notes/:n
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
$ curl -si -X POST -d x=1 localhost:4170/blog    # no route at all: the answer from before this chapter
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD

# a build whose only extra route is POST /directory; GET /directory is a dynamic() page
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:4170/directory   # without the route
200
$ curl -si localhost:4171/directory | head -5                         # with it

Content-Type: text/plain; charset=utf-8
Content-Length: 19

Allow: POST

Reading bodies#

Why the obvious version is wrong. The server read a request with one tcp_read. That is one read(2) of at most 64 KiB, and it does not wait. Calling it in a loop until it returns nothing does not help. A body sent after its headers is not in the socket yet when the loop looks. That includes curl waiting on Expect: 100-continue, and a proxy that streams. So the loop would end early, with a short body and no error. The framework reads to a count instead:

  1. GET and HEAD are passed on exactly as they were read. Their bodies are not read.
  2. For anything else, web_read_rest waits with tcp_poll and reads until the headers have ended and Content-Length bytes of body are in. It gives up after WEB_READ_MS (2000 ms), counted from the first read.
  3. Once the headers are in, the body is short, and the request says Expect: 100-continue, it writes HTTP/1.1 100 Continue once.
  4. It stops at once, without reading the body, when the request is chunked, its Content-Length is not a number, or its Content-Length is over the limit.
  5. web_frame_error then turns what was read into a refusal or lets it through (table below).
  6. web_parse_body runs on every request a route matched, before the pipeline:
    • application/x-www-form-urlencoded → body_params
    • application/json → json, and also body_params when it is an object. Bad JSON is 400.
    • multipart/* → 415
    • anything else: the raw body, nothing parsed
$ curl -sv -H 'Expect: 100-continue' -H 'Content-Type: application/json' --data-binary @big.json localhost:4170/api/notes
> Expect: 100-continue
< HTTP/1.1 100 Continue
< HTTP/1.1 201 Created

Framing is lenient, in two ways that matter. The body is everything after the blank line, not Content-Length bytes of it. So extra bytes end up in the body. And a POST with no Content-Length gets whatever arrived in the first read as its body. HTTP says such a request has no body. The server closes every connection after one response, so this cannot desynchronise a pipeline. It can make a well-formed body fail to parse:

$ printf 'POST /api/notes HTTP/1.1\r\nHost: x\r\nContent-Type: application/json\r\nContent-Length: 14\r\n\r\n{"text":"abc"}GARBAGE' | nc -w 3 localhost 4170 | tail -1
the body is not JSON: SyntaxError at line 1, column 15
$ printf 'POST /api/notes HTTP/1.1\r\nHost: x\r\nContent-Type: application/json\r\n\r\n{"text":"no length"}' | nc -w 3 localhost 4170 | tail -1
{"saved":"no length","words":2}

Sessions#

The cookie

_blimp_session=<payload>.<mac>; Path=/; HttpOnly; Secure; SameSite=Lax

payload = base64url(json_encode(session))
mac     = hex(HMAC-SHA256(secret, "blimp-session." <> payload))
  • Signed, not encrypted. Anyone holding the cookie can read the session (decoded here). Nobody without the secret can write one. The "blimp-session." prefix means a MAC made for another purpose with the same secret, such as the comparison MACs below, is never a valid session MAC.
  • Verification splits on .. A real cookie has exactly two parts, because base64url and hex have no dot. It then checks the MAC before decoding anything. If the payload does not decode to a JSON object, the result is also :tampered.
  • A tampered cookie gets the log line web: a session cookie failed its MAC on POST /notes. The request carries on with no session, so under WEB_BROWSER the CSRF check then fails with a 403. The bad cookie is not deleted. It is replaced the next time something writes the session.
  • Set-Cookie is sent only when the session changed (session_dirty). An empty session is sent as a deletion (Max-Age=0).
  • 4000 bytes at most. A session that signs to a longer cookie is a 500, not a truncated cookie: 
    $ curl -si -b j4 -d "_csrf_token=$T&text=$(python3 -c "print('x'*3000)")" localhost:4170/notes | sed -n '1p;$p'
HTTP/1.1 500 Internal Server Error
the session is too large for its cookie
# server log: web: the session outgrew its cookie on POST /notes
  • Secure: browsers keep the cookie over plain HTTP only on localhost. See In a browser.
  • No expiry. The cookie has no Max-Age, so the browser drops it when it closes (depending on the browser's session restore). The server accepts it forever, because the payload carries no time. Rotating SESSION_SECRET is the only way to revoke sessions, and it revokes all of them.

SESSION_SECRET

The secret is read once, at boot (WEB_SECRET = web_session_secret() in main.blimp):

  • If DATABASE_URL is set, which is how the site recognises production, and SESSION_SECRET is unset, the site refuses to start. A default secret there would let anyone who has read 41_web.blimp sign a session.
  • If it is set but under 32 bytes, the site refuses to start, with or without a database.
  • If neither is set, as on a laptop or in the tests, it uses a fixed dev secret and says so in the boot log.
$ DATABASE_URL=postgres://nobody@127.0.0.1:1/x blimp --serve _build/site-4171.blimp --tick "site <- :tick"
"SESSION_SECRET is not set, and DATABASE_URL is: refusing to start with a guessable session key"
# exit 1
$ SESSION_SECRET=short DATABASE_URL=postgres://nobody@127.0.0.1:1/x blimp --serve _build/site-4171.blimp --tick "site <- :tick"
"SESSION_SECRET is under 32 bytes: refusing to start"
# exit 1
$ blimp --serve _build/site-4170.blimp --tick "site <- :tick"
SESSION_SECRET is not set: sessions are signed with the dev secret (DATABASE_URL is unset, so this is not production)

Deploying PR #100 therefore needs SESSION_SECRET in the server's environment, /opt/blog/.env and the compose file. Without it the production site does not come back up. The refusal fires before the database is touched.

CSRF#

  • The token is 32 random bytes in base64url, stored in the session as "_csrf_token". web_ensure_csrf makes it the first time a page asks for it, and it stays the same for the life of the session.
  • Where it goes: in a form, a hidden field named _csrf_token. For fetch(), put it in <meta name="csrf-token" content="..."> and send it back as the x-csrf-token header. A JSON body may also carry it as a "_csrf_token" key. If the header is present it wins, and the body is not looked at.
  • What is checked: every method except GET, HEAD and OPTIONS, on routes whose pipeline includes web_protect_from_forgery. The request passes if the session has a token, the sent token is a non-empty string, and the two are equal. A failure is 403 "invalid CSRF token" with the log line web: CSRF token missing or wrong on POST /notes. Four cases fail: no token, another session's token, no cookie, and a tampered cookie. The tests cover all four.
  • Why the comparison is not ==. == on two strings stops at the first byte that differs, so its timing tells an attacker how much of a guess was right. web_secure_eq compares HMAC(secret, "blimp-eq." <> a) with the same for b. Where two MACs first differ has nothing to do with where a and b differ.
  • Not masked. Phoenix XORs the token with a fresh mask on every render. This does not, so the same 43 characters appear on every page of a session. If a page that includes attacker-controlled text is ever served compressed, the token can be recovered byte by byte (BREACH).

The API opt-out, and why it is safe

WEB_API swaps the token check for web_require_json. A cross-site <form> can only send three content types: urlencoded, multipart and text/plain. It cannot send application/json. A cross-site fetch() that sets application/json is preflighted with OPTIONS, and this server answers every OPTIONS with a 405, so the preflight fails and the browser never sends the request. A JSON request that reaches the handler therefore came from a page on this site, or from something that is not a browser and has no victim's cookie to use. DELETE is let through without the content type because a cross-site DELETE is preflighted too. I checked this in headless Chrome. A page on http://127.0.0.1:8765 made three fetch() calls with credentials: "include" to the server on localhost:4170. The server log shows what arrived:

POST   /api/notes   application/json  -> Failed to fetch
DELETE /web/echo/1                    -> Failed to fetch
POST   /api/notes   text/plain        -> Failed to fetch

# server log
OPTIONS /api/notes 405 0ms
OPTIONS /web/echo/1 405 0ms
POST /api/notes 415 1ms

The JSON POST and the DELETE never got past their preflight. The text/plain POST is a "simple" request, so the browser sent it without a preflight, and web_require_json refused it. The page could not read any of the three answers.

The session is still fetched, so an API route can see who is logged in:

$ curl -s -b jar -H 'Content-Type: application/json' -d '"s"' localhost:4170/web/api/echo
{"json":"s","session":"ok"}
$ curl -s -H 'Content-Type: application/json' -d '[1,2]' localhost:4170/web/api/echo
{"json":[1,2],"session":"none"}

A route with the pipeline [] has neither protection. Use it only for endpoints that are safe to call from anywhere.
