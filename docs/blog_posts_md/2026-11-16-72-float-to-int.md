# The Float one past maxInt

*November 16, 2026*

If you write the biggest Int as a Float in Blimp, you get a number one bigger than the biggest Int. Until this chapter, handing that number to `to_int` took the whole interpreter down.

```blimp
print(to_int(9223372036854775807.0))
```

On the parent branch:

```
thread 8575568 panic: integer part of floating point value out of bounds
exit 134
```

A 64-bit double has 53 bits of mantissa, so up near 2^63 the doubles are 1024 apart. 9223372036854775807 (maxInt) falls between two of them and rounds up to 9223372036854775808, which is 2^63. You can see it from Blimp:

```blimp
print(9223372036854775807.0)
print(9223372036854775807.0 == 9223372036854775808.0)
```

```
9223372036854776000
true
```

That first line is how `print` spells 2^63, the shortest digits that round-trip, and it reads like a number that would fit in an Int even though it is one past the top.

## The half that never crashed

Issue #29 was about the abort: `to_int`, `floor`, `ceil` and `round` all ended in a bare `@intFromFloat`, and Zig's safety check on that builtin panics when the integer part doesn't fit. While probing it, we found the other half. The safety check catches out-of-range values and lets NaN through, so a ReleaseSafe build returns whatever the arm64 instruction produces, which is 0.

```blimp
print(to_int(sqrt(-1.0)))
print(floor(sqrt(-1.0)))
```

On the parent branch that printed `0` twice and exited 0, so your program kept going with a zero that nothing in it ever computed. Of the two halves, we think this is the worse one, because the abort at least leaves you a stack trace pointing at `builtinToInt`.

## What it does now

All four builtins go through one helper in `src/builtins.zig`:

```zig
fn intOfFloat(comptime func: []const u8, whole: f64) EvalError!i64 {
    const two_63: f64 = 9223372036854775808.0;
    if (std.math.isNan(whole)) return failArg(func ++ ": NaN has no Int value", .{});
    if (!(whole >= -two_63 and whole < two_63))
        return failArg(func ++ ": {d} is outside Int's range, -2^63 to 2^63-1", .{whole});
    return @intFromFloat(whole);
}
```

Each builtin rounds its own way first (`@trunc` for `to_int`, then `@floor`, `@ceil`, `@round`) and hands the whole-valued Float to the helper. The comparison happens in Floats, over the half-open range from -2^63 up to but not including 2^63. The low end is exact, since -2^63 is a double and is minInt, so `to_int(-9223372036854775808.0)` still gives you minInt. The high end has to be a strict `<` against 2^63, because maxInt has no double to compare against. NaN fails both comparisons, and the `isNan` check runs first so it gets its own message.

`failArg` is the path every builtin uses when it can't take an argument, so the result is an ordinary Blimp error box:

```
-- BAD ARGUMENT ──────────────────────────────────

  floor: -inf is outside Int's range, -2^63 to 2^63-1

1| print(floor(-exp(1000.0)))
           ^
```

and you can catch it:

```blimp
r = try do
  to_int(sqrt(-1.0))
catch err do
  err
end
print(r)
```

```
:type_error
```

We ran every awkward input through all four builtins, on the parent and on this branch. The two edges that fit, `9223372036854774784.0` (the last double below 2^63) and `-9223372036854775808.0`, convert exactly on both. Everything past them, plus 1e20, both infinities and NaN, went from a panic (or a silent 0 for NaN) to `:type_error`. In-range behaviour is the same: `-2.5` gives -2, -3, -2, -3 for `to_int`, `floor`, `ceil` and `round`.

## Why refuse instead of clamp

Saturating is the obvious fix, and the issue itself called it defensible. With it, `to_int(1e20)` would come back as 9223372036854775807 and `to_int(NaN)` as 0, which keeps the NaN bug on purpose and adds a second one shaped like it.

Wrapping is what Blimp picked for Int arithmetic in #27, and `9223372036854775807 + 1` prints `-9223372036854775808` today. That choice followed the LLVM backend, which already wrapped. Float conversion has no backend to follow, and infinity has no wrapped value to give back.

A dedicated `:out_of_range` error would say more, but it needs a new `EvalError` variant and a slot in the evaluator's try/catch atom table for something four builtins use. The String version settled it: `to_int("100000000000000000000")` already refused with `:type_error`. Now `to_int(100000000000000000000.0)` gives the same answer, and the change stays inside `builtins.zig`. The test file `test/float_to_int_test.blimp` checks the two spellings agree.

## The compiler side

We built `blimp-compile` against LLVM 22 to see what it does with the same programs, and it does nothing, because it has no Float-to-Int conversion. `to_int(1.5)` fails LLVM verification (`call i64 @to_int(double 1.500000e+00)`), `floor(2.5)` fails the same way, `to_int(3)` fails at link time with an undefined `_to_int`, and even the list `[1.5]` fails verification. The C runtime's `blimp_val_to_int` casts with `(long long)v->float_val`, which C leaves undefined out of range, but no compiled program can produce a Float to reach it yet, so the chapter leaves it alone. The differential harness from the previous chapter already lists `to_int(1.5)` as a compile error.

## Still broken

`sum()` drops Floats: `sum([1.5, 2])` is 2 and `sum([1.5])` is 0. That turned up during the probing and isn't fixed here.

`9223372036854775808` still won't lex (`Parse error: error.InvalidNumber`), so minInt in source is still `0 - 9223372036854775807 - 1`. Issue #29 mentions that, and it's why we haven't closed the issue on this chapter alone.

One correction to our own notes. The commit message said `1e30` doesn't lex, and the new test file's header said the same about `1e20`. Both were wrong, and we have since corrected both. Exponent literals have lexed since the September commit "a float may carry an exponent": `type_of(1e30)` is `:float`, `print(1e400)` prints `inf`, and `to_int(1e20)` is `:type_error` on this branch. The tests could spell infinity `1e400` instead of `exp(1000.0)`. They still work as written.

To try it, build with Zig 0.16.0 from `chunks/lang`:

```
zig build interp
zig-out/bin/blimp test test
```

That runs 70 tests in 8 files, 11 of them in `float_to_int_test.blimp`.
