# The Int You Could Not Write

*November 16, 2026*

Blimp's Int runs from -9223372036854775808 to 9223372036854775807, and until this chapter you could not type the first of those numbers. Two of our own documents said why, and both had it wrong. Chapter 72's post said `9223372036854775808` "won't lex", and issue #29 blamed the lexer too. The lexer reads that string as an ordinary integer token, like any other run of digits. The parser was what refused it, in `parsePrimary`:

```zig
const value = std.fmt.parseInt(i64, self.current.lexeme, 10) catch return error.InvalidNumber;
```

2^63 does not fit in an i64, so `parseInt` fails, and the user saw this:

```
$ echo 'print(-9223372036854775808)' > m.blimp && blimp m.blimp
Parse error: error.InvalidNumber at line 1, col 8
```

The column is all it gave you. The minus sign never got a chance, because the parser reads the operand before it applies the negation, and the operand on its own is one more than the largest Int. So minInt had to be spelled `0 - 9223372036854775807 - 1`, which is how the overflow tests from #27 still spell it.

## Where the minus goes

The fix that comes to mind first is to parse the digits as something wider, an i128 or a u64, and negate later. That breaks on the case where there is no minus. A bare `9223372036854775808` has to become something. If it wraps to minInt, then `0 - 9223372036854775808` evaluates to `0 - minInt`, which wraps back to minInt, and the program runs on with a number nobody wrote. If it becomes a Float, it turns into `9223372036854775808.0` and changes type in the middle of Int arithmetic. Either way the program gets a different number from the one in its source.

So this branch does what Java does with its long literal. In `parseUnary`, a unary minus followed by the digits of 2^63 is folded into one `integer_lit` whose value is minInt, before any binary operator sees the token. Leading zeros and a space after the minus are allowed. Anywhere else, the magnitude is a parse error, and now the error says what is wrong:

```
$ echo 'print(0 - 9223372036854775808)' > m.blimp && blimp m.blimp
Parse error at line 1, col 11: integer literal 9223372036854775808 is one more than
the largest Int, 9223372036854775807; it is an Int only as the operand of a unary
minus, `-9223372036854775808`, not after a binary one as in `x - 9223372036854775808`
```

The literal works everywhere an expression goes. We tried it as a function argument and as a `case` pattern:

```blimp
x = 0 - 9223372036854775807 - 1
r = case x do
  -9223372036854775808 -> "min"
  _ -> "other"
end
print(r)
```

That prints `"min"` on this branch. On chapter 77 it was a parse error at line 3. Arithmetic on the literal wraps the way #27 settled: `-9223372036854775808 - 1` prints `9223372036854775807`, and `-9223372036854775808 / -1` prints `-9223372036854775808`.

`5 -9223372036854775808` is refused, though 5 - 2^63 fits in an Int. In that expression the minus is binary and the literal is the thing being subtracted. We checked the neighbours here. rustc says `literal out of range for i64` about `5 -9223372036854775808` and accepts `-9223372036854775808`. javac says `integer number too large` for `5 - 9223372036854775808L` and prints minInt for `- 9223372036854775808L`. Go accepts the subtraction and prints `-9223372036854775803`, but only because Go constants have arbitrary precision until they are assigned. Blimp has no constant arithmetic, so it would have nothing to do the subtraction in.

The compiler uses the same parser, so it picked up the literal with no codegen change. `blimp-compile` on a file containing `-9223372036854775808` prints that number. The differential harness from chapter 71 has two new corpus programs on the literal, and the interpreter and the compiler agree on both.

## The Blimp parser written in Blimp

`lib/` has a lexer and a parser written in Blimp itself, as actors. Its `parse_primary` called `to_int(lexeme)` on every integer token. `to_int` raises a TypeError for digits past maxInt, and the error stopped the Parser actor. A test calling it got `TypeError while evaluating this.` and nothing about the literal. This branch adds the same fold to its `parse_unary` and moves the conversion into a `parse_integer` that catches the TypeError and returns a refusal:

```
%{ok: false, error: "integer literal 9223372036854775808 is one more than the largest Int, 9223372036854775807; it is an Int only as the operand of a unary minus", pos: 2}
```

The message is shorter than the Zig parser's. It ends before the two example spellings.

## sum, abs and range

`sum` added the Ints in a list and skipped everything else. `sum([1.5, 2])` was 2, `sum([0.1, 0.2])` was 0, and `sum([1, :a])` was 1. Each of those is the right total for some other list. Now `sum` is the left fold of `+` starting from 0. Ints wrap until the first Float, the total is a Float after that, and an item `+` would reject, such as an atom, `nil`, `true` or a list, raises a TypeError that `try` catches as `:type_error`.

The simpler rule, converting the whole total to Float once a Float shows up, gives the wrong answer for `[9223372036854775807, 1, 0.5]`. Written out as `9223372036854775807 + 1 + 0.5`, Blimp wraps the Int addition first and prints `-9223372036854776000`. Converting early would give roughly 2^63 instead. Following `+` in order keeps `sum` and the fold equal, and a test in `lib/builtin_test.blimp` checks that list.

`abs(-0.0)` was `-0.0`. The code was `if (f < 0) -f else f`, and negative zero is not less than zero. `@abs` clears the sign bit. Nothing had caught it because `abs(-0.0) == 0.0` is true either way, so the new test compares `to_string`, where the sign shows: `"-0"` before, `"0"` now.

`range` panicked when it ended at maxInt:

```
$ echo 'print(range(9223372036854775806, 9223372036854775807))' > r.blimp && blimp r.blimp
thread 11012843 panic: integer overflow
src/builtins.zig:1110:49: ... in builtinRange (blimp)
```

The loop counter was incremented once past the end. #27 chose wrapping for arithmetic a program asks for, but the program never asked for maxInt + 1. Now the length is computed in i128 and each item is `start + i`. The two-item range above works, and `range(-9223372036854775808, 0)`, which asks for 2^63 + 1 items, reports `OutOfMemory` instead of panicking.

## What is still not right

None of the three builtin fixes reach compiled code. `blimp-compile` has no `range` at all (the link fails on `_range`). `sum` fails LLVM verification even on a list of Ints, and so does `abs(-0.0)`. The type checker does not know that `sum` can return a Float, so `max(sum([1.5, 2]), 1)` gets past it and fails at run time, where `max(1.5, 2)` is caught before the program starts. `--9223372036854775808` is still `error.UnexpectedToken` with no explanation, the same as `--5`.

With the literal in, nothing issue #29 reports still fails. Chapter 72 made the float conversions catchable, and exponent literals had lexed since September, before the issue was filed. This chapter closes it.
