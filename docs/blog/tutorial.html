learn blimp

From zero to a live app in your browser. Every code block runs -- edit and hit Run.

1. Values

Blimp has integers, floats, strings, booleans, atoms, nil, lists, tuples, and maps.

Atoms are like symbols. They start with : and are used for messages, tags, and enums.

2. Variables and Math

Bind with =. All the usual operators work.

Strings concatenate with concat.

3. Lists

Lists are the workhorse. Built-in functions operate on them.

4. Functions

Define named functions with def. Anonymous functions with fn.

5. Map, Filter, Reduce

Pass functions to transform lists.

6. Pipes

Chain operations with |>. The result of the left flows into the first argument of the right.

7. Loops

for iterates over a list and collects results. each iterates for side effects.

Use for to transform -- it returns a new list.

Use each with a function when you want to do something with each item (like send messages to actors -- you'll see this soon).

8. Pattern Matching

situation matches a value against patterns. First match wins.

9. Maps

Key-value data. Look things up, add keys, get all keys.

10. Actors

Here is where Blimp gets interesting. An actor is a thing that holds state and responds to messages.

actor defines a template. spawn creates a live instance. <- sends a message. become updates state.

Actors can have multiple handlers and return values.

11. Views

View functions return view_node values -- a tree that describes UI. They compose by nesting.

12. Actors as Components

When an actor's :view handler returns a view tree, it becomes a UI component. button("label", :message) sends a message back to the actor. become updates state. The view re-renders.

The buttons are live. Tap them.

13. Always-On Systems

Actors don't just respond to button clicks. In a real system, actors send messages to each other. You can use loops to drive a stream of activity through a network of actors.

10 jobs processed, 10 log entries. Two actors, each tracking their own state, driven by a loop. In a running system, these messages come from users, timers, network events -- the actors don't care where messages come from.

Actors watching actors

Build systems where actors coordinate. A monitor checks the worker's output. A supervisor restarts things. Each actor is a small, independent piece.

Each actor is its own process with its own state. They don't share memory. They communicate only through messages. This is how you build systems that don't break.

The pattern

Every always-on system in Blimp follows the same shape:

1. Define actors -- each one owns a piece of state

2. Spawn them -- they come alive with default state

3. Drive messages -- loops, user input, timers, other actors

4. Actors react -- become updates state, reply returns data

5. Add a view -- one actor renders the dashboard

14. The Coffee Shop

Put it all together. Five actors, a dashboard view, live buttons. This is a complete app.

Five actors running. Tap the buttons -- revenue climbs, sales tick up. Each actor holds its own state. The view re-renders on every message.

What's Next

You just built a multi-actor app with live UI from your phone. The core ideas:

1. Actors hold state -- become updates it

2. Messages are atoms -- <- sends them

3. Views are values -- functions that return a tree

4. Buttons send messages -- the actor re-renders
