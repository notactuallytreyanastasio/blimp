blimp

an actor language for people who build things

Blimp is a programming language where your code structure is your runtime structure. There are no modules, no classes, no namespaces pretending to be boundaries. There are actors. They hold state, they receive messages, they respond. The hierarchy you write is the supervision tree that keeps your system alive.

The language compiles to native code via LLVM and runs in the browser via WebAssembly. The REPL is the development environment. The canvas shows your system breathing. Every example on this page is live. Hit Run and watch.

"you are the craftsperson with a beautiful team of helpers that make you work at the speed of thought"

Values

Blimp has the types you'd expect. Integers, floats, strings, booleans, atoms, lists, tuples, maps. Nothing surprising here. The point isn't novelty in the data model. The point is what you do with it.

Atoms start with a colon and represent themselves. They're your enums, your status codes, your message names. Cheap to compare, impossible to misspell at runtime because the compiler checks them.

Functions and Pipes

Functions are defined with def. Parameters require type annotations. Always. The compiler rejects untyped parameters at compile time, no exceptions. This was a deliberate decision -- we audited every parameter position in the language (handlers, defs, lambdas) and closed every hole.

The pipe operator |> threads a value through a chain of function calls. The underscore _ marks where the piped value goes. This solves the "which argument position" problem that plagues every other pipe implementation.

Lambdas are first-class. map, filter, reduce do what you think. Lambda parameters need types too.

Actors: The Only Abstraction

There are no modules in Blimp. No classes. No structs separate from behavior. There are actors. An actor holds state, defines message handlers, and communicates via <-. That's it. That's the whole language.

This isn't a limitation. It's the point. When your only tool for organizing code is the thing that also defines your runtime behavior, your code structure and your system architecture are the same thing. You can't have them drift apart.

Three things happened above that matter:

become is the only way to change state. No mutation. No assignment to fields. You declare the new state and the runtime transitions atomically. This means every state transition is a snapshot. History is queryable. Time travel debugging works by replaying become transitions.

<- is a blocking message send. The sender waits for a reply. This is synchronous by default because it's the sane default. Async is opt-in, not the other way around.

Defining the actor didn't spawn it. actor Counter do ... end registers a template. The first message send Counter <- :increment auto-spawns the singleton. spawn Counter creates additional instances. The canvas only shows actors that are alive.

Supervision via Dot Notation

In Blimp, your namespace IS your supervision tree. Shop.Checkout isn't just a naming convention. It means Checkout is a child process of Shop. When Shop dies, Checkout dies. When Shop restarts, Checkout restarts.

Watch the canvas. Three hexagons appear: Shop, Shop.Inventory, Shop.Checkout. The hierarchy is visible. Message rays animate from you to each actor. State fields update in real time. This is the system, breathing.

Design decision: Dot notation was a parser fix that took 3 files. The parser only accepted lowercase identifiers after a dot. We added upper_identifier handling in parsePostfix, flattened DotAccess chains in the evaluator and type checker. Simple change, deep consequence: your code layout IS your runtime topology.

Views: UI is a Message Response

In Blimp, rendering a view is just responding to a message. An actor has an on :render handler that returns a view tree. The framework sends :render, gets back a tree, diffs it against the previous tree, and patches the DOM.

This means time-travel debugging works on your UI for free. Replay the state transitions, re-send :render, get the view at any point in history.

17 view primitives: stack, row, grid for layout. text, heading, bold, italic, code, code_block, blockquote, divider, list for content. link, image for media. button, input, textarea, select for interaction. They compose. They nest. They're just function calls that return view nodes.

Actors That Render

The real power: mount(Actor) composes actor views. Each actor manages its own state and renders its own view. The framework routes messages to the right actor. No prop drilling. No state management library. Just actors.

The Web Framework is Written in Blimp

The HTTP server is pure Blimp. TCP socket builtins (tcp_listen, tcp_accept, tcp_read, tcp_write, tcp_close) are implemented in Zig. Everything above that -- request parsing, routing, session management, HTML rendering, form handling -- is Blimp code.

The server is an actor. Sessions are an actor. The app is composed of actors. There's no framework separate from the language. The language IS the framework.

WebSocket smart reloads are coming. The architecture mirrors Phoenix LiveView: persistent WebSocket connection, server-side view diffing via view_diff(old, new), minimal JSON patches sent to the client. The builtins exist (ws_accept_key, ws_read_frame, ws_write_frame). The client JS has exponential-backoff reconnect. What's missing is the concurrent connection handler -- the single-threaded evaluator blocks on I/O. The actor scheduler (Phase 4 of the runtime plan) fixes this.

The Hole Operator

This is the weird one. Blimp has first-class support for incomplete code.

A situation block with a wildcard _ branch containing a comment directive is a Hole. At runtime, when execution reaches the Hole, the evaluator builds a prompt from the directive, the current state, and visible bindings. It shells out to Claude. Claude generates the missing code. The evaluator patches the source file, replaces the Hole with real code, and re-executes.

The second run uses the generated code directly. The Hole is gone. Your codebase grew.

Testing

Blimp has a built-in test runner inspired by ExUnit. Test blocks live inside actors. The suite actor IS the test runtime -- its state fields are the fixture, re-evaluated fresh for each test.

blimp_test(code) parses, evaluates, and runs tests at runtime. It returns a map: %{passed: true, total: 1, passed_count: 1, failure: ""}. The interactive tutorial uses this to validate your code in the browser.

The Runtime

Memory: Per-Actor Arenas

Each actor owns an arena allocator. All allocations during a handler go into the actor's arena. become reuses memory in place when the refcount is 1 (Perceus reference counting). When an actor dies, its entire arena is freed in O(1). No GC pauses. No fragmentation across actor boundaries.

Scheduling: Reduction Counting

Every operation costs one reduction. After 4,000 reductions, the actor yields. The scheduler saves its full stack, moves it to the back of the FIFO run queue, and picks up the next actor. This is the BEAM model. Predictable latency. No actor can starve others.

Compilation: Zig to LLVM to Native

The compiler is written in Zig. The pipeline: source -> lexer -> parser (recursive descent) -> AST (58 node kinds) -> type checker (2-pass cross-actor registry) -> tree-walking evaluator (for REPL/WASM) -> LLVM IR codegen (for native). The native compiler produces binaries that run at 1-2x C performance on recursive benchmarks.

WASM: 178KB in the Browser

The entire language -- parser, evaluator, builtins, type checker, test runner -- compiles to a 178KB WebAssembly module. Every example on this page runs in your browser. The canvas visualization runs alongside it. No server required.

The Canvas

The canvas is the compiler's visual artifact. When you run Blimp code, the canvas shows the living system: actors as generative hexagons (fill pattern hashed from actor state), message sends as animated rays with trailing heads and impact rings, the REPL as a pulsing origin blob, supervision hierarchy through spatial grouping.

This isn't a debugging tool bolted on after the fact. It's produced by the compiler. Every evaluation step feeds the canvas. The canvas IS the program, visualized.

Go back up and run the Counter or Shop examples. Watch the hexagons appear. Watch the rays fire. That's your program running.

Self-Hosting

The dream: Blimp compiles Blimp.

The compiler is currently written in Zig. The WASM REPL runs the evaluator in the browser. The web framework is written in Blimp. The test runner runs Blimp tests written in Blimp. The tutorial teaches Blimp inside a Blimp REPL running on a Blimp WASM module.

The path to self-hosting:

  • Phase 1 (done): Zig compiler, tree-walking evaluator, WASM target
  • Phase 2 (done): Web framework in Blimp, test runner in Blimp
  • Phase 3 (next): Actor scheduler, concurrent connections, WebSocket push
  • Phase 4: Blimp parser written in Blimp (the evaluator can parse and eval strings already via blimp_eval)
  • Phase 5: Blimp codegen written in Blimp, targeting WASM
  • Phase 6: The compiler compiles itself. Blimp contains itself.

When that happens, the browser REPL compiles your code, the tutorial teaches with live compilation, and the whole thing fits in under 200KB.

Why

We are building things differently now. The code you write will be read by agents, modified by agents, reviewed by agents. The programmer's job isn't typing characters. It's making decisions. Blimp is a language for that world.

Actors are the right abstraction because they're the thing that maps to both human reasoning ("this component does X") and runtime behavior ("this process handles X"). Modules don't run. Classes are blueprints for things that run. Actors run. Your code IS the running system.

The Hole operator is the bridge. Incomplete code isn't an error, it's a request. The language knows what's missing and asks for help. The agent fills it in. The programmer approves. The decision is captured in the graph.

"I still want to craft software. I just want to do it at the speed of thought."

Blimp borrows Ruby's surface and Elixir's data model and then puts something new underneath the two of them. Every handler has three beats: compute with pipes, transition with become, communicate with reply. The canvas shows you what's alive. The test runner proves it works. The web framework ships it.
